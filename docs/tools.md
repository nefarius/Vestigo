# MCP tools

Point an MCP client at `http://127.0.0.1:5098/mcp` (Streamable HTTP). When `ApiTokens` is set, send `Authorization: Bearer <token>`. The generated parameter catalog is [generated/mcp-tools.md](generated/mcp-tools.md).

## Offline

`get_trace_settings` returns the effective input and output roots, whether the built-in `traces` folder is in use, the `traces` named root, the symbol cache, the symbol server URL (userinfo and query string removed) and where it came from (`setting`, `environment`, or `none`), whether symbol-server authentication is configured (scheme only), `AttachableSessions`, and the size limits. It never returns tokens or the symbol-server secret. Call it before uploading symbols or starting a capture.

`inspect_wpp_pdb` returns WPP control GUIDs, names, and flag bits from one PDB.

`validate_decoding_sources` loads explicit PDB and TMF paths and reports whether a decoding context was built.

`scan_etl_metadata` returns the distinct PDB name, GUID, age, and symbol-server index prefix referenced by the ETL files.

`resolve_binary_symbols` reads the CodeView (RSDS) identity from each `.sys`, `.dll`, or `.exe` that lies in a Files root with `Read` access, then resolves that PDB through the symbol cache, the trace input roots, and the configured symbol server. Each result reports the identity, origin (`Cache`, `LocalSearch`, `SymbolServer`, or `Unresolved`), local PDB path, and a failure code when resolution missed (`no_codeview`, `not_found`, `symbols_unresolved`, or `symbol_auth_failed`).

`extract_trace_archive` extracts `.pdb`, `.tmf`, and `.etl` entries from a zip inside an allowed input root into a directory inside the allowed output roots (the built-in `traces` folder when defaults are in use). Other entries are skipped. Absolute paths, `..`, drive letters, and alternate-data-stream names are refused (`unsafe_entry`). Entry count, uncompressed size, and a 200:1 compression ratio are capped. Existing files are kept unless `overwrite` is true.

`convert_etl` writes `json` or `ndjson` under an allowed output root. The tool result is a summary: path, event count, bytes, missing WPP formats, truncation, and symbol diagnostics. It does not return the trace payload. When the output file also lies in a root with `Read` access it adds a `download` link (a one-time ticket when `ApiTokens` is set); fetch the file with it instead of an API token. A 401 or 403 from the symbol server fails the conversion with `symbol_auth_failed`.

## Realtime

`list_etw_sessions` returns every session name Windows reports. It does not stop sessions.

`start_capture` accepts provider GUIDs and/or PDB paths. PDB control GUIDs are enabled automatically. TMF files contribute message formats but not provider GUIDs. Optional `binaryPaths` (installed `.sys`, `.dll`, or `.exe` files) are resolved like `resolve_binary_symbols` and then treated as extra PDB paths; if any binary cannot be resolved the capture is not started (`no_codeview`, `symbols_unresolved`, or `symbol_auth_failed`). The call returns when the session has started, not when the trace ends. Keyword bitmasks accept a decimal value or a `0x` hexadecimal value. The level must be a named `TraceLevelSelection` value.

`list_captures` and `get_capture` report state, event count, bytes, missing formats, and the stop reason.

`read_capture` returns NDJSON lines after `afterSequence`. Pass the returned `NextSequence` to the next call. `limit` is clamped to `MaxReadBatch`.

To follow a capture live, loop on `read_capture` with `waitSeconds` greater than zero (clamped to `MaxReadWait`). The call returns as soon as new events are spooled, or empty at the timeout, and stops waiting when the capture ends. Each page carries `State` and `Completed`; stop looping when `Completed` is true.

`attach_etw_session` attaches read-only to an existing realtime session that is not owned by Vestigo, such as one started by `tracelog`, and decodes its events with optional PDB or TMF paths and the same optional `binaryPaths` as `start_capture`. The session name must match `Vestigo:AttachableSessions` (empty by default, which disables attach). The job appears in `list_captures` with `Mode` `Attached` and is read with `read_capture`. `stop_capture` only detaches; the session itself is never stopped, and it is never recorded as a Vestigo-owned session.

`stop_capture` cancels the reader and disposes the ETW session.

Capture duration cannot exceed `MaxCaptureDuration`. The spool is removed after `SpoolRetention` once the capture has stopped.

## Debug output

The `DebugOutput` module is disabled by default. It runs the bundled DebugViewConsole (DebugView++ 1.30.0.0) and forwards Win32 `OutputDebugString` messages to the calling agent. Only one capture runs at a time; a second `start_debug_capture` fails with `capture_busy`. Read [security.md](security.md#debug-output) first.

`start_debug_capture` starts DebugViewConsole with capture-time substring filters (`includeMessages`, `excludeMessages`, `includeProcesses`, `excludeProcesses`) and an optional `duration` capped by `Vestigo:DebugOutput:MaxDuration`. The call returns when the process has been launched, not when capture ends. A successful launch may already be `Running` or `Failed`; that status does not guarantee the capture is ready. If another DebugView instance owns `DBWIN_BUFFER`, the capture ultimately records `Failed` with `dbwin_in_use`.

`list_debug_captures` and `get_debug_capture` report state, message count, bytes, the child PID, and the stop reason.

`read_debug_output` returns NDJSON lines after `afterSequence`. Each line is `{receivedAt, time, pid, processName, message}`. Pass the returned `NextSequence` to the next call. `limit` is clamped to `MaxReadBatch`. To follow a capture live, loop with `waitSeconds` greater than zero (clamped to `MaxReadWait`) and stop when `Completed` is true. Optional read-time filters (`messageRegex`, `excludeRegex`, `processIds`, `processNames` globs) skip non-matching lines; `nextSequence` still advances past every scanned line. Regexes use `RegexOptions.NonBacktracking | IgnoreCase`.

`stop_debug_capture` sends Ctrl+C to DebugViewConsole and then kills the process tree.

Windows allows only one `DBWIN_BUFFER` reader per session. Another DebugView or DebugView++ instance causes the capture to fail with `dbwin_in_use` after launch. Processes that have a debugger attached send their output to the debugger instead of this capture. Kernel `DbgPrint` is not captured.

## Services

The `Services` module lists and controls Win32 services and kernel/file-system drivers. Names are service names, not display names. States are `stopped`, `start_pending`, `stop_pending`, `running`, `continue_pending`, `pause_pending` and `paused`. Start types are `boot`, `system`, `auto`, `demand` and `disabled`; `boot` and `system` are only valid for drivers.

`list_services` filters by `kind` (`win32`, `driver`, `all`), `nameContains` (name or display name) and `state`, sorted by name and capped by `limit` (default 200, maximum 1000; the result reports `Total` and `Truncated`). `get_service` adds the error control, exit codes and, while running, the process id. `start_service`, `stop_service` and `restart_service` wait for `running` or `stopped` for up to `timeoutSeconds` (maximum 300; 0 returns immediately on start and stop) and return a `timeout` error with the last state otherwise. `stop_service` with `stopDependents` stops running dependents first; without it a service with running dependents fails with `has_dependents`. Starting or stopping a service that is already in the target state succeeds without a call. `set_service_start_type` changes the start type through `ChangeServiceConfig`.

`create_driver_service` and `delete_service` use the bundled nefcon runner and only handle `KERNEL_DRIVER` services. `create_driver_service` needs an existing `.sys` file reachable through a root that allows `Execute` (`root:relative\path` or an absolute path inside such a root); `delete_service` takes a plain name and refuses Win32 and file-system driver services. A result with `RebootRequired` means the change completes after a restart.

Driver caveats: Windows only loads signed kernel drivers, so `start_service` on an unsigned driver fails with `driver_signature` (error 577) or `driver_blocked` (1275) unless test-signing mode is enabled or the driver carries a valid signature. Use `get_boot_security` to see the BCD value and the running kernel state; `set_test_signing` writes the default boot entry when `Vestigo:System:AllowBootConfigurationChanges` is true, then reboot. Secure Boot blocks test signing. A driver that starts and immediately stops is reported as `timeout`; check `get_service` for the exit code. Mutating tools refuse the names in `Vestigo:Services:ProtectedNames`. They need the elevated service account; otherwise they return `access_denied`.

## Scheduled tasks

The `ScheduledTasks` module lists, inspects, and controls Windows scheduled tasks through the Task Scheduler 2.0 service on this machine. Task paths start with a backslash, for example `\Vendor\Nightly`; a missing leading backslash is added, and paths with `..`, doubled backslashes, quotes, or wildcard characters are refused with `invalid_path`. States are `unknown`, `disabled`, `queued`, `ready` and `running`.

`list_scheduled_tasks` takes a `folder` (default `\`), `recurse` (default true), `includeHidden`, `nameContains` (matched against the task path) and `state`, sorted by path and capped by `limit` (default 200, maximum 1000; the result reports `Total` and `Truncated`). `get_scheduled_task` adds the principal (user or group, logon type, run level), the actions (command, arguments, working directory, or COM handler class id), the triggers, key settings, and the full definition XML. `get_scheduled_task_history` returns recent events for one task from the `Microsoft-Windows-TaskScheduler/Operational` log, newest first; it fails with `history_disabled` when that channel is not enabled, which is the Windows default on many machines.

`run_scheduled_task`, `stop_scheduled_task`, `enable_scheduled_task`, `disable_scheduled_task` and `delete_scheduled_task` are refused with `changes_disabled` unless `Vestigo:ScheduledTasks:AllowChanges` is `true`. `run_scheduled_task` starts the task now, optionally with `arguments` for the task's `$(Arg0)` placeholders. The task runs as its own principal, often SYSTEM, not as the Vestigo service account. `wait` (0 to 300 seconds) waits for it to leave `running` and then reports `LastTaskResult`; if it is still running, `StillRunning` is true. Running a disabled task returns `task_disabled`, and a task that is already running returns `already_running`. `delete_scheduled_task` and `disable_scheduled_task` refuse tasks below `Vestigo:ScheduledTasks:ProtectedPaths` (default `\Microsoft\Windows\`) with `protected_task`; run, stop and enable stay allowed there. Vestigo does not create or edit tasks. Changing tools need the elevated service account; otherwise they return `access_denied`.
## Software

The `Software` module inventories installed programs from the `Uninstall` registry keys: `HKLM` in the 64-bit and 32-bit views plus every loaded user hive. Entries without a display name are skipped. Each entry has an `Id` such as `machine-x64:{KeyName}`, `machine-x86:{KeyName}` or `user:<SID>:{KeyName}`, and reports name, version, publisher, install date, install location and source, `UninstallString`, `QuietUninstallString`, size, scope, architecture, MSI product code and the detected installer type (`msi`, `burn`, `inno`, `nsis`, `installshield`, `unknown`).

`list_installed_software` filters by `nameContains`, `publisherContains` and `scope` (`machine`, `user`, `all`); system components and updates (entries with a parent) are hidden unless `includeSystemComponents` or `includeUpdates` is set. Results are sorted by name and capped by `limit` (default 200, maximum 1000). `get_installed_software` adds the silent command Vestigo would run, or why none exists.

`uninstall_software` runs a silent uninstall as a job (see [Jobs](#jobs)). It is refused with `uninstall_disabled` unless `Vestigo:Software:AllowUninstall` is `true`. MSI products always run `msiexec.exe /x {ProductCode} /qn /norestart /l*v <log>` (the stored string is often `/I`). Other entries use `QuietUninstallString` when present, otherwise known switches are appended for Burn (`/uninstall /quiet /norestart`), Inno Setup (`/VERYSILENT /SUPPRESSMSGBOXES /NORESTART`) and NSIS (`/S`); other installers return `unsupported_installer`. Uninstallers in locations that non-administrators can modify are refused with `untrusted_executable`. `dryRun` returns the plan only; `wait` (0 to 300 seconds) waits and returns the exit code, `RebootRequired` (exit 3010 or 1641 count as success), whether the entry is `StillInstalled`, and the output tail including the MSI log. A run is killed after `Vestigo:Software:MaxUninstallDuration`. Entries that are `NoRemove`, system components, per-user, or match `Vestigo:Software:ProtectedNames` (default `Vestigo`, matched against the display name) are refused.

## Environment

`get_environment_variable` reads one variable from `machine` (`HKLM\SYSTEM\CurrentControlSet\Control\Session Manager\Environment`), `user` (the registry hive of the user logged on at the console) or `process` scope. Registry values are returned unexpanded with their kind (`REG_SZ` or `REG_EXPAND_SZ`). User scope fails with `user_not_available` when nobody is logged on. `list_environment_variables` lists a scope, optionally names only.

`set_environment_variable` takes an `operation` of `set`, `unset`, `append` or `prepend`. Append and prepend treat the value as `;`-separated entries (for example `PATH`), skip entries that are already present, and keep an existing `REG_EXPAND_SZ` kind. `expand` writes `REG_EXPAND_SZ` for `set`. A change to machine or user scope broadcasts `WM_SETTINGCHANGE`; the result reports `broadcast` as `sent`, `timeout` or `skipped`. Names in `Vestigo:Environment:ProtectedNames` are refused with `protected_name`. The value is never echoed or logged.

## System

The `System` module reports the host Windows version, boot state, boot-security posture, and UAC policy. Version and boot-security reads go through `Nefarius.Utilities.WindowsVersion`. It is enabled by default. Boot-configuration writes stay off until `Vestigo:System:AllowBootConfigurationChanges` is `true`. UAC writes stay off until `Vestigo:System:AllowUacChanges` is `true`.

`get_system_info` returns the OS name, edition, display version (for example 24H2), version string, major/minor/build/UBR, whether it is Windows 11 or Server, whether the install was in-place upgraded (`grandfathered`), OS and processor bitness, ARM64, whether UAC is disabled, and the machine name. A probe that fails becomes a null field instead of failing the call.

`get_boot_state` returns `uptimeSeconds` from `GetTickCount64`, `lastBootUpTimeUtc` (UTC now minus that tick count, so a clock change moves it), `fastStartupEnabled` (`HKLM\SYSTEM\CurrentControlSet\Control\Session Manager\Power\HiberbootEnabled`), `safeMode` (`normal`, `safe`, or `network` from `SM_CLEANBOOT`), and `pendingFileRenameCount`. `fastStartupEnabled` is null when the value is absent or not a DWORD, and zero is the only false value. It is the Fast Startup configuration. It does not say whether the previous boot restored a hiberfile. `pendingFileRenameCount` is the number of source/destination pairs in `PendingFileRenameOperations` and `PendingFileRenameOperations2`. It is null when the Session Manager key or a value cannot be read, and zero when both values are absent or empty. The paths stay in `list_pending_file_operations`. A failed probe is a null field. There is no reboot tool.

`get_boot_security` returns `uefi`, `secureBoot`, `testSigningConfigured` (BCD on the default boot entry), `testSigningActive` (the running kernel), `whqlDeveloperTestMode`, and `rebootPending` when the BCD value and the running state differ. `notes` explain Secure Boot blocking test signing, a pending reboot, and that BCD changes apply only to the default boot entry. WHQL developer test mode is not present on every Windows build; a missing value is null.

`set_test_signing` and `set_whql_developer_test_mode` fail with `boot_changes_disabled` unless the option is enabled. Turning test signing on fails with `secure_boot_enabled` unless Secure Boot is known to be disabled. A BCD write failure is `bcd_write_failed`; a WHQL policy write failure is `ci_write_failed`; lack of elevation is `access_denied`. Vestigo never reboots the machine: BCD test-signing takes effect at the next boot, and WHQL developer test mode availability depends on the Windows build.

`get_uac` reads `HKLM\SOFTWARE\Microsoft\Windows\CurrentVersion\Policies\System` and maps `EnableLUA`, `ConsentPromptBehaviorAdmin`, and `PromptOnSecureDesktop` to a slider level: `always` (2, secure desktop on), `default` (5, secure desktop on), `noDim` (5, secure desktop off), `never` (0, secure desktop off), or `disabled` (`EnableLUA` is 0). Any other combination is `custom`. The result also returns `ConsentPromptBehaviorUser` and notes that Group Policy can override these values and that `EnableLUA` changes apply after a reboot.

`set_uac` accepts `always`, `default`, `noDim`, `never`, or `disabled` and fails with `uac_changes_disabled` unless the option is enabled. `custom` and any other string fail with `invalid_level`. Slider levels write `EnableLUA=1` plus the matching prompt values and leave `ConsentPromptBehaviorUser` alone. `disabled` writes only `EnableLUA=0`, so the previous slider position is kept, and it reports `rebootRequired`. Turning UAC off also breaks UWP and Store apps until it is turned back on. A registry write failure is `uac_write_failed`; lack of elevation is `access_denied`. Vestigo never reboots the machine.

`list_logon_sessions` lists Windows logon sessions: session id, window station name, connection state, user, logon time, whether the session is the active console, and whether interactive tools would attach to it (`isCurrentInput`). `includeDisconnected` defaults to true. `includeListeners` defaults to false, so listener rows such as `RDP-Tcp` are omitted. `includeClientAddresses` defaults to false: the client name and address are null unless it is true, and those values are not written to the log. Station names are displayed, not interpreted. There is no logoff, connect, or shadow tool.

`get_logon_session` returns one session id from that list. It adds token elevation (`default`, `full`, `limited`, or `unknown`), whether the token is in the local Administrators group, and the logon id, when the session token can be opened. Those three fields are null when the token cannot be read; the rest of the session is still returned. A negative id is `invalid_request`. An id Windows did not return is `session_not_found`. A refused query is `access_denied`. A Terminal Services failure is `wts_unavailable`. Protocol names are `console`, `ica`, `rdp`, or `unknown`.

## Power

The `Power` module is enabled by default. It is read-only. There is no scheme change, sleep, hibernate, or shutdown tool.

`get_power_state` returns `acLineStatus` (`online`, `offline`, or `unknown`), `batteryPresent`, `batteryPercent`, `batteryCharging`, `batteryTimeRemainingSeconds`, `activeSchemeGuid`, `activeSchemeName`, `lastSleepTimeUtc`, `lastWakeTimeUtc`, and `capabilities`. `batteryCharging` is separate from AC status: a battery can be charging while `acLineStatus` is `offline`. When no battery is present, or the battery status is unknown, the battery percent, charging flag, and remaining time are null. `lastSleepTimeUtc` and `lastWakeTimeUtc` are UTC now minus the `LastSleepTime` and `LastWakeTime` interrupt-time counters, so a clock change moves them. A zero counter is null. `capabilities.fastStartupSupported` means the platform can use Fast Startup. Whether it is configured is `get_boot_state` `fastStartupEnabled`. `capabilities.modernStandby` is `AoAc`. A failed probe is a null field. The call fails with `power_api_failed` only when the power read throws.

`get_sleep_configuration` returns the active scheme's AC and DC values for lid close (`doNothing`, `sleep`, `hibernate`, `shutdown`, or `unknown`), standby, hibernate, and monitor timeouts in seconds, wake timers, and hybrid sleep. A timeout of 0 means never. A value Windows did not return is null. Null is not `doNothing` and it is not zero. `doNothing` is only lid index 0 (`PowerActionNone`).

## Updates

The `Updates` module is enabled by default. Checking the signed Buildbot feed is always available while the module is on. Installing a release stays off until `Vestigo:Updates:AllowSelfUpdate` is `true`, and it also needs the MSI `Automatic updates` feature so `Nefarius_Vestigo_Updater.exe` is present. Read [security.md](security.md#updates) first.

`check_for_updates` downloads `https://buildbot.nefarius.at/builds/Vestigo/latest/updates.json` and `updates.json.minisig` as the service account, verifies the sidecar with the Nefarius minisign public key, refuses any URL outside that Buildbot directory, and compares the newest enabled release to the installed version. The installed version is `HKLM\SOFTWARE\Nefarius Software Solutions\Vestigo\Version` when the updater feature wrote it, otherwise the entry assembly informational version. The result also reports whether the packaged updater is installed, whether self-update is allowed, and the last `start_self_update` attempt (exit code, inferred success when the installed version now matches the target, and the log tail).

`start_self_update` is refused with `self_update_disabled` unless the option is enabled. It re-checks the signed feed and returns `up_to_date` without launching when no newer release exists. Otherwise it starts the packaged Vicius updater with `--silent-update --skip-self-update --ignore-busy-state --ignore-postpone --log-to-file`. The updater copies itself to `%TEMP%` and the original process exits `207` before the MSI stops the Vestigo service, so the MCP session drops. `dryRun` returns the planned command only. A second call while an updater process is running returns `update_in_progress`. Missing updater files are `updater_not_installed`; an updater that Users can modify is `untrusted_executable`; a non-success Vicius exit is `updater_failed`. Logs and the last-attempt record live under `%ProgramData%\Nefarius Software Solutions\Vestigo\updates`.

## Logs

`tail_text_file` returns the last `lines` lines of a file under a root with `Read` access, examining at most `maxBytes` from the end (both clamped to `Vestigo:Logs`). The file is opened with shared access. UTF-8 and UTF-16 byte order marks are detected; otherwise UTF-8 is assumed. The result has `lines`, a `cursor` (`offset`, `length`, `identity` = creation time ticks), `truncated` and `encoding`.

`read_text_file_since` continues from `offset` and `identity` of a previous cursor and returns complete lines only; an unterminated last line waits until it is finished. If the file is shorter than the offset or its identity changed, reading restarts at the beginning and `rotated` is true. Page with `maxLines` while `hasMore` is true. A single line longer than the byte cap is returned in pieces with `truncated` set.

`read_json_path` reads one UTF-8 JSON document under a root with `Read` access and returns the values selected by a bounded query. A query may be `$`, `$.name`, `$['key']` (quotes are required for hyphens, dots, and other characters outside an identifier), `$[0]`, or the same forms with one trailing `.*` or `[*]` wildcard. Filters, slices, unions, and recursive descent are rejected with `invalid_query`, and the error names the supported subset. A wildcard returns every child in document order, capped by `Vestigo:Logs:MaxJsonMatches`, with `truncated` set when later matches were left out. An empty object or array wildcard succeeds with no matches. A missing name or index is `query_no_match`. The result carries `matches` (`matchedAt`, `type`, `value`, `serializedBytes`, `valueOmitted`), the document `sha256`, `rootType`, and the capped `topLevelKeys`. `matchedAt` is the normalized JSONPath location, such as `$['status']` or `$['items'][0]['name']`. JsonPath.Net parses the query; Vestigo then allows only names, non-negative indexes, and one trailing wildcard. `value` is the JSON value itself. A JSON null is a value; `value` is absent only when `valueOmitted` is true. One match larger than `Vestigo:Logs:MaxJsonValueBytes` fails with `value_too_large` and does not return the value. A wildcard match over that limit is listed with its type and size and `valueOmitted: true`. `maxBytes` can only lower `Vestigo:Logs:MaxJsonBytes`. A larger file fails with `file_too_large` before its contents are read.

`get_json_summary` answers what is in the document without a query. An object lists each top-level property with its type and serialized size (`memberCount`, `truncated` when the list is capped). An array reports `length` and does not list elements. A string, number, boolean, or null reports `rootType` only. Use `$.*` or `$[*]` with `read_json_path` to read those elements.

Both tools accept one JSON value, not NDJSON. A second value, a comment, truncated JSON, or a repeated property name is `invalid_json`. A syntax error includes the document byte offset. A duplicate property name is reported without the name. Neither error includes the document text. Line-oriented NDJSON stays with `search_text`. Path errors are the same as `tail_text_file` (`outside_root`, `not_found`, `access_denied`, `unknown_root`), and a directory is `not_a_file`.

`search_text` filters large or numerous text files on the machine with the bundled [ripgrep](https://github.com/BurntSushi/ripgrep) (`tools\rg.exe`) so only the interesting lines cross the network. `path` is a file or a directory (searched recursively) under a root with `Read` access. `pattern` is a Rust regular expression, or literal text with `fixedStrings`; `ignoreCase`, `wholeWord`, `contextBefore` and `contextAfter` refine the match, `maxMatchesPerFile` caps matches per file, and `globs` such as `*.log` or `!*.old.log` pick files below a directory. Hidden files are searched, `.gitignore` rules are not applied, links and junctions are not followed, binary files are skipped, and UTF-8 and UTF-16 (byte order mark) files are decoded. The result has `lines` (`path`, `line`, `text`, `isMatch`, `textTruncated`), `matchCount`, `truncated`, `timedOut`, `bytesSearched` (known when ripgrep finished by itself), `elapsedMilliseconds` and `warnings` (for example files ripgrep could not read). Output is bounded by `Vestigo:Logs`: `MaxSearchResults` lines, `MaxSearchContextLines`, `MaxSearchLineLength` (longer lines are cut to a window around the first match) and `MaxSearchDuration`. When `truncated` or `timedOut` is true, ripgrep was stopped early; narrow the pattern, path or globs and search again. Use `tail_text_file` or `read_text_file_since` to follow a file as it grows. Failures use stable codes: `invalid_request`, `invalid_pattern`, `executable_missing`, `hash_mismatch`, `search_busy` and `search_failed` (see [troubleshooting.md](troubleshooting.md#text-search-fails)).

## Registry

`read_registry_value`, `list_registry_values`, and `get_registry_metadata` read one registry key under an allow-listed prefix. The module is off until `Vestigo:Modules:Registry:Enabled` is true. There is no write tool. `view` is `registry64` or `registry32`; the service process bitness does not choose the view. `HKLM` and `HKEY_LOCAL_MACHINE` are the same hive, as are `HKU` and `HKEY_USERS`. `HKCU` is the user logged on at the console (`HKU\<sid>`), and it fails with `no_interactive_session` and a `reason` when nobody is logged on. `HKCR` and `HKCC` are rejected with `invalid_request`.

An empty `Vestigo:Registry:AllowedPrefixes` uses the built-in Windows locations (device guard, session manager, device class, services, system policy, and the uninstall keys). A non-empty list replaces that set. Add a vendor root such as `HKLM\SOFTWARE\<Vendor>\<Product>` when a lab needs it. `DeniedPrefixes` always includes `HKLM\SAM`, `HKLM\SECURITY`, `HKLM\SYSTEM\CurrentControlSet\Control\Lsa`, and `HKLM\SOFTWARE\Microsoft\Windows NT\CurrentVersion\Winlogon`, and configured entries are added to that list. A denied prefix wins even when an allow prefix also matches. Matching is case-insensitive and stops at a backslash boundary, so `HKLM\SOFTWARE\Contoso` does not allow `HKLM\SOFTWARE\ContosoEvil`.

`read_registry_value` returns one value. Omit `value` for the key default. `REG_SZ` and `REG_EXPAND_SZ` return `text`. `expand` expands a `REG_EXPAND_SZ` as the service account. `REG_MULTI_SZ` returns `values`. `REG_DWORD` and `REG_QWORD` return `number`. `REG_BINARY` returns `sha256` when the value fits `Vestigo:Registry:MaxBinaryBytes`, and `hex` only when `includeBinary` is true. A larger binary or string fails with `value_too_large` before the bytes are allocated, and the error does not include the value. `list_registry_values` returns values and child names. `recurse` walks nested keys and is clamped down to `MaxRecursionDepth`. `maxEntries` can only lower `MaxEntries`. `truncated` is true when the cap stopped the walk. A child outside the allow list, or on the deny list, is omitted. `get_registry_metadata` returns `lastWriteUtc`, `subKeyCount`, and `valueCount` and does not read values or the key's security descriptor. Values are returned to the client and are not written to the log. A registry symbolic link can still open a target outside the prefix; the prefix check is on the path you asked for, not on the link target.

## Event log

`list_event_logs` lists channels with record count and enabled state, optionally filtered by `nameContains`.

`query_event_log` reads a channel (`Application`, `System`, ...) or an `.evtx` file under a root with `Read` access. Filters `providers`, `levels` (`critical`, `error`, `warning`, `information`, `verbose`), `eventIds`, `since` and `until` (ISO 8601) are turned into an XPath that is returned as `query`; alternatively pass a raw `xpath` (not combined with filters). `messageContains` filters the rendered message after reading and is bounded by `Vestigo:EventLog:MaxScannedEvents` (`scanLimitReached`). Results are newest first by default and capped by `Vestigo:EventLog:MaxEvents`; `truncated` says more matched. Messages are null when the publisher is not installed. `includeXml` adds the raw event XML.

## Jobs

`list_jobs`, `get_job`, `wait_job`, `read_job_output` and `cancel_job` manage background jobs that other tools start. `read_job_output` returns text after a byte `offset`; pass the returned `NextOffset` to continue. Finished jobs are kept for `JobRetention`.

## Files

Paths are `root:relative\path` (or an absolute path inside a root). Reads need `Read`, everything that changes files needs `Write`. A root, or a directory containing a root, can never be deleted or moved, and NTFS stream syntax (`file:stream`) is rejected.

`list_roots` returns each root with its access flags and free space. `list_directory` lists a directory (`maxEntries` up to 5000, `Truncated` tells you more exist). `stat_path` returns size and times, an optional SHA-256, and for `.exe`, `.dll` and `.sys` files the version resource plus Authenticode status (`Signed`, `Unsigned`, `Invalid`, `Untrusted`, or `Unavailable`) and `source` (`embedded`, `catalog`, or `none`). Verification uses cache-only revocation and does not contact the network. A catalog-signed Windows file is `Signed` with `source: catalog`. `Unavailable` means the check could not be completed; it is not `Unsigned`.

`copy_path`, `move_path`, `delete_path` (non-empty directories need `recursive`) and `make_directory` do what they say. Directory copies skip links.

`fetch_file` imports an HTTP(S) URL or an ordinary UNC file (not `\\?\` or `\\.\` device paths) onto this host, into a root, as a background job; use `wait_job` and `read_job_output`. It does not export a screenshot or other file to the MCP client. Pass `expectedSha256` to reject a wrong file, and `overwrite` to replace an existing one. The size is capped by `Vestigo:Files:MaxUploadBytes`.

`get_upload_url` returns the `PUT` URL for a root-relative path plus ready-to-run `curl.exe` and `Invoke-WebRequest` commands. `get_download_url` returns the URL only, not the file bytes, for an existing file in a root with `Read` access. When `ApiTokens` is set, both URLs carry a one-time `ticket` (see below), so the API token never has to be copied into a client command or a chat. `delete_file_on_reboot` schedules a deletion with `MoveFileEx(MOVEFILE_DELAY_UNTIL_REBOOT)`; the service must run elevated.

### HTTP transfer endpoints

When `ApiTokens` is set, both endpoints accept either `Authorization: Bearer <token>` (permanent access) or a one-time `?ticket=` query parameter. Without `ApiTokens` they are anonymous and no ticket is minted.

Tickets are minted by the MCP tools that prepare a file for transfer: `get_download_url`, `get_upload_url`, `take_screenshot` with `saveTo`, and `convert_etl` when its output also lies in a root with `Read` access. Those results carry a `download` (or `link`) object with `url`, `expiresUtc`, `singleUse`, `curl` and `powershell`. A ticket is bound to one method, one resolved file path and, for uploads, the `overwrite` and `deferToReboot` values chosen when it was issued (the query string cannot change them). It expires after `Vestigo:Files:TicketLifetime` (default 15 minutes) and becomes invalid as soon as one transfer completes successfully. A failed or aborted transfer leaves it usable until it expires. Ticketed downloads stream the whole file and do not support `Range`. Responses are sent with `Cache-Control: no-store`. Tickets live in memory only, so a service restart invalidates them. An unknown, expired, used or mismatched ticket returns 401 `invalid_ticket`.

`PUT /files/{root}/{path}?overwrite=false&deferToReboot=false` streams the request body to a temporary file in the target directory and commits it with an atomic replace. An optional `X-Content-SHA256` header is checked before the commit; a mismatch returns 422 and writes nothing. The response is JSON:

```json
{ "fullPath": "D:\\drops\\bin\\x.sys", "size": 11, "sha256": "...", "replacedExisting": false, "rebootRequired": false, "asideFile": null, "asideCleanup": null }
```

If the target is locked, for example a loaded driver or running executable, the old file is renamed to `<name>.vestigo-old-<guid>`, the new file takes its place, and the old one is deleted or scheduled for deletion at reboot (`asideCleanup`). With `deferToReboot=true` the new file instead becomes a pending replace through `MoveFileEx(DELAY_UNTIL_REBOOT | REPLACE_EXISTING)` and `rebootRequired` is `true`. If the file cannot be renamed either, the call fails with 423 and suggests `deferToReboot`. Status codes: 400 invalid path, 403 root lacks `Write`, 404 unknown root, 409 exists without `overwrite`, 413 over `MaxUploadBytes`, 422 hash mismatch.

`GET /files/{root}/{path}` streams a file from a root with `Read` access and supports `Range` requests.

## Diagnostics

The `Diagnostics` module is disabled by default (`Vestigo:Modules:Diagnostics:Enabled`). It inspects PE files inside a root with `Read` access, lists modules loaded in a process, reads SetupAPI history, explains a device problem code, and inventories graphics adapters, process connections, media capabilities, and Windows Error Reporting metadata. Capture probes, network probes, audible audio probes, and process dumps stay off until their own gates are on. A valid Authenticode signature does not mean Windows will load the file as a kernel driver. Read [security.md](security.md#diagnostics) first.

`inspect_binary` reads one PE through [PeNet](https://github.com/secana/PeNet): architecture (`x86`, `x64`, `arm64`, `armnt`, `arm64ec`, `arm64x`), `PE32` or `PE32+`, subsystem, selected DLL characteristics, timestamp, whether a CLR header is present, the CodeView PDB file name (never a directory), file and product version, size, and SHA-256. A file that is not a PE fails with `not_pe`. A broken PE fails with `malformed_pe`. Files larger than `Vestigo:Diagnostics:MaxInspectBytes` fail with `file_too_large`. Every field comes from one open of the file. This tool does not verify a signature.

`verify_file_signature` checks the embedded Authenticode signature and, when the file has none, the Windows catalog. `outcome` is `unsigned`, `valid`, `invalid`, `untrusted`, or `unavailable`. `source` is `embedded`, `catalog`, or `none`. `revocation` is `none`, `cacheOnly` (the default; no network), or `online`. `online` fails with `revocation_not_allowed` unless `Vestigo:Diagnostics:AllowOnlineRevocation` is set, and it may contact revocation servers. Signer subject, issuer, and thumbprint are returned only when `includeSigner` is true.

`list_process_modules` returns a best-effort snapshot: name, size, architecture, and version. `baseAddress` is omitted when process memory is not readable. `includePaths` returns `root:relative` aliases for modules inside a root with `Read` access. Modules outside those roots have `path: null` and `pathOutsideRoots: true`. Absolute paths are never returned. Hashing and signature checks are separate calls to `inspect_binary` or `verify_file_signature`. Pass `expectedStartTime` from `list_processes` to reject a reused pid (`process_identity_mismatch`). `partial` means some modules were skipped. Protected processes fail with `access_denied`.

`get_device_install_history` reads only `%windir%\INF\setupapi.dev.log` and rotated `setupapi.dev.*.log` files. It does not take a path. A section matches when the instance ID equals the whole token after the last ` - ` in the `>>>  [...]` header, case-insensitively. A hardware ID that appears only in the section body does not match, and a longer token does not match as a substring. Each section returns its title, start, end, exit status, the original numeric codes, INF and driver-version lines, and the log file name. `complete` is false when the section has no section-end and exit-status pair. `includeRaw` adds the section text, capped per section; otherwise those lines are omitted from the result. The read is capped by `Vestigo:Diagnostics:MaxInstallHistoryBytes`, keeps the newest bytes, and sets `truncated` when older text was skipped. `since` drops sections that end before that time. `limit` keeps the newest matches and returns them oldest first. This tool does not rank drivers.

`explain_device_problem` reports `observed` facts from the device node, class filters, the device's service, Kernel-PnP configuration events, and the latest install sections. Boot security is included for problem code 52. `explanation` is the documented meaning of a covered CM_PROB code (1, 10, 18, 19, 22, 24, 28, 31, 37, 39, 43, 45, 52). `hypotheses` are labeled and cite that evidence. An uncovered code sets `insufficientEvidence` and does not guess. The result makes no claim about driver ranking. Service, event, and boot facts are `unavailable` when those modules are disabled. Device queries work without enabling the Devices module.

`list_graphics_adapters` enumerates DXGI adapters in the service process, including software (WARP or Basic Render) and remote adapters. Each adapter returns description, vendor, device, subsystem, and revision when those ids are non-zero, the adapter LUID, dedicated and shared memory, and the user-mode driver version when `CheckInterfaceSupport` returns one. Each output lists the adapter LUID it is attached to. A Display-class device node is matched by PCI ids. `matchConfidence` is `exact`, `subsystem`, `device`, or `ambiguous`. Unknown numbers are null. This tool does not rank drivers.

`probe_capture_support` asks whether frames arrive for `target` (`primary` or a GDI device name) using `backend` `dxgi` (Desktop Duplication) in the console user's session. `durationMs` is capped by `Vestigo:Diagnostics:MaxProbeDuration`. The result reports `sessionId`, `desktopName`, what the API advertised, frames arrived, first-frame latency, and the final HRESULT (`DXGI_ERROR_ACCESS_LOST`, `DXGI_ERROR_NOT_CURRENTLY_AVAILABLE`, `DXGI_ERROR_UNSUPPORTED`, or `E_ACCESSDENIED` when those codes are returned). Frame arrival is an observation and proves no cause. No pixel data is returned or logged. The tool fails with `probes_disabled` until `Vestigo:Diagnostics:AllowCaptureProbes` is true, and with `user_not_available` when nobody is logged on. `backend` `wgc` returns `unsupported`: Windows Graphics Capture is not implemented in this build.

`list_process_connections` returns the TCP endpoints and UDP bindings owned by one process: protocol, address family, TCP state when known, and the local address and port. `includeRemoteAddresses` adds the remote address and port; otherwise those fields are null and are not written to the log. A UDP row is a local binding and does not prove that a peer is reachable. No packet payloads, headers, or credentials are read. Pass `expectedStartTime` from `list_processes` to reject a reused pid (`process_identity_mismatch`). `limit` is clamped to `Vestigo:Diagnostics:MaxProcessConnections`.

`test_endpoint` observes one destination from Vestigo's own network context, which can differ from an application's routing, proxy, or credentials. `protocol` `dns` resolves the host, `tcp` also connects, and `tls` also performs a TLS handshake. Certificate name and chain validation stay enabled. Online revocation runs only when `Vestigo:Diagnostics:AllowOnlineRevocation` is true; otherwise revocation is not checked. Chain building can still download a missing issuer certificate from an Authority Information Access URL. An untrusted or mismatched certificate is reported as `authenticated: false` and is not accepted. `timeoutMs` is capped by `Vestigo:Diagnostics:MaxEndpointProbeDuration`. `includeResolvedAddress` reports the addresses used. The tool fails with `network_probes_disabled` until `Vestigo:Diagnostics:AllowNetworkProbes` is true, and with `destination_not_allowed` unless the host, or the host and port, is listed in `Vestigo:Diagnostics:AllowedProbeDestinations`. The allow-list has no wildcards or ranges. A TCP result is not a measure of media quality, jitter, or loss. No payloads, headers, or credentials are returned.

`list_video_encoders` enumerates video encoders with Media Foundation `MFTEnumEx`. `backend` must be `media-foundation`; any other value returns `unsupported` and does not query a vendor encoder SDK. The result is labeled `discoverySource: MFTEnumEx` and `stage: enumerated`. Transforms are not activated and no frames are submitted, so this is not proof that an encoder can process a frame, and it is not a complete inventory of encoders that do not register an MFT. `limit` is clamped to `Vestigo:Diagnostics:MaxVideoEncoders`.

`list_camera_formats` lists video-capture devices. Omit `device` to return names and symbolic links without activating a source (`stage: enumerated`). Pass a symbolic link or a friendly name to activate that one source, read the media types it advertises, and shut it down (`stage: advertised`). No sample is read, so the tool does not record the camera. A camera may still indicate that it is active while the source is open. More than one device with the same friendly name returns `ambiguous_device`; pass the symbolic link. `limit` is clamped to `Vestigo:Diagnostics:MaxCameraFormats`.

`probe_audio_format` checks whether an endpoint supports a shared-mode PCM format (`pcm-rate-16-channels`, for example `pcm-48000-16-2`). `endpoint` is an endpoint id or `default-render`. The format check does not start the stream and does not emit sound. `playback: true` renders a 440 Hz tone for `durationMs` only when `Vestigo:Diagnostics:AllowAudioPlayback` is true, and only on a render endpoint; otherwise the tool returns `audio_playback_disabled`. The probe runs in the console user's session, uses shared mode, and does not change the default endpoint, record a microphone, or open a loopback capture. `stage` is `activated` for a format check and `processed` when synthetic samples were written. The result names the format, duration, `backend: wasapi`, and `workload` `format-check` or `synthetic-tone`. It is not a measurement of application performance. `durationMs` is capped by `Vestigo:Diagnostics:MaxAudioProbeDuration`.

`list_crash_reports` reads Windows Error Reporting `ReportArchive` and `ReportQueue` metadata from the fixed machine store, the service profiles, and each user profile. It does not take a path. `scope` is `machine`, `user`, or `all`. Each row returns the store, a profile label, the folder name, event type, event time, application name and path, report id, and up to 16 signature values. A dump file beside a report is returned as a file name and length only. Dump bytes and the raw `Report.wer` text are not returned. `since` drops reports with no event time and reports earlier than that time. `limit` is clamped to `Vestigo:Diagnostics:MaxCrashReports`. The list is a metadata snapshot and does not explain the crash.

`capture_process_dump` writes a minidump of one process as a job. It fails with `process_dumps_disabled` until `Vestigo:Diagnostics:AllowProcessDumps` is true. `output` must be a new `.dmp` file in a root with `Write` access. `expectedStartTime`, from `list_processes`, is required and is checked again immediately before the write. `dumpType` `mini` writes a small snapshot. `dumpType` `full` writes process memory and can contain credentials that were in that process. The dump runs as the Vestigo service. The service itself, pid 4, a fixed list of critical processes, and protected processes are refused with `protected_process`. The output volume must still have `Vestigo:Diagnostics:MinDumpFreeBytes` free after reserving `Vestigo:Diagnostics:MaxDumpBytes`; otherwise the tool returns `insufficient_disk_space`. A dump larger than the cap is deleted and the job reports `dump_too_large`. If that partial file remains, the job also reports `cleanup_failed`. Vestigo does not upload the file and does not create a download ticket. `wait` is seconds from 0 to 300. The job output is a status line, never dump bytes. The Diagnostics module requires Jobs.

## Processes

The `Processes` module is disabled by default and requires the `Jobs` module. These tools run arbitrary code by design; read [security.md](security.md#processes) first. Enabling it without `ApiTokens` is allowed and logs a startup `SECURITY WARNING`.

`run_process` starts a process as a job. `path` is a file under a root with `Execute` access (`name:relative\path` or an absolute path inside such a root), or a bare name such as `cmd.exe` resolved from the service `PATH` when `Vestigo:Processes:AllowPathLookup` is true (the default). `args` is an array; each element is quoted for `CommandLineToArgvW`. `workingDirectory` must be under a root with `Read` access and defaults to the executable's directory. `env` overrides environment variables. `.ps1` files run through `pwsh.exe` when it is installed, otherwise `powershell.exe`, with `-NoProfile -ExecutionPolicy Bypass -File`.

`context` is `service` (default, the service account, normally SYSTEM) or `interactive` (the active console user on `winsta0\default`). `elevated: true` with `interactive` uses the user's linked administrator token; it returns `elevation_unavailable` for a standard user. When nobody is logged on at the console, interactive requests fail up front with `no_interactive_session` and a `reason` (`nobody_logged_on`, `only_disconnected_sessions`, `session_0_only`, or `console_session_has_no_token`) and no job is created. Screenshot, input, audio, and diagnostic probes use the same `reason`. Probes and user-scope environment keep the code `user_not_available`. stdout and stderr are appended to the job output and stdin is NUL. Console programs write in the OEM code page, so non-ASCII output may be garbled.

`wait` is seconds (0 to 300). With `wait` greater than 0 the call waits that long and returns the job state plus the last 16 KB of output; `StillRunning` tells you whether the job outlived the wait. With `wait` 0 it returns the job id immediately; use `wait_job`, `read_job_output` and `cancel_job`. `cancel_job` kills the whole process tree. Interactive processes run in a job object with kill-on-close, and the job tree is ended when their output passes `MaxJobOutputBytes`, so descendants also end when the main process exits.

`list_processes` returns pid, name, session id and start time, filtered by `nameFilter` (substring), `pid` or `sessionId`.

`close_app` posts `WM_CLOSE` to visible top-level windows selected by `pid`, `processName` and/or `titleRegex` (pid or name, narrowed by the title pattern). Windows belong to a desktop, so the default `interactive` context starts `Vestigo.exe --session-helper close-window ...` in the console user's session; it prints JSON and exits. After `gracefulTimeoutSeconds` the result lists the processes that are still alive (`StillRunning`); Vestigo never kills them. Use `elevated: true` to close elevated windows. `context: service` only sees the service's own desktop.

`kill_process` terminates by `pid` or exact `processName` (every match). `entireTree` also kills descendants. It refuses its own pid, pid 0 and pid 4.

## Desktop

The `Desktop` module is disabled by default. It lists Win32 windows and the GDI/physical displays they are rendered on, and can take screenshots of that desktop and describe it for an agent with `inspect_screen` and `find_on_screen`. Window titles and screen contents from the console user's desktop are information disclosure; read [security.md](security.md#desktop) first. Enabling it without `ApiTokens` is allowed and logs a startup `SECURITY WARNING`. Screenshots stay off until `Vestigo:Desktop:AllowScreenshots` is `true`.

`list_windows` returns each matching window's handle (hex), title, class, owning process (pid, name, path when `PROCESS_QUERY_LIMITED_INFORMATION` is allowed), parent (null when the parent is the desktop), owner, root owner, visibility, minimized/maximized/cloaked, `GetWindowRect` bounds, DWM extended-frame bounds, client size, window DPI, nearest GDI display (`\\.\DISPLAY1`), and every display its bounds intersect. Coordinates are physical pixels: the enumerator switches the thread to per-monitor DPI awareness for the call.

Filters combine: `pid` or `processName`, narrowed by `titleRegex` and `className`. `includeHidden` adds invisible windows; cloaked windows (for example an app on another virtual desktop) still appear when they are visible to `IsWindowVisible`. `includeChildren` also walks `EnumChildWindows`; child-window titles are omitted so control text is not returned or matched. `limit` is 1 to 5000 (default 500); `truncated` is true when the cap was hit. A `titleRegex` that exceeds its one-second match limit fails with `invalid_request`.

Windows belong to a desktop, so the default `interactive` context starts `Vestigo.exe --session-helper list-windows` in the console user's session; it prints JSON and exits. `context: service` only sees the service's own desktop (session 0 when Vestigo runs as a service). Interactive enumeration needs a console user; it fails with `no_interactive_session` otherwise. Secure and locked desktops are not visible. `ProcessPath` may be null for protected processes. Titles are read with `SendMessageTimeout` so a hung window cannot stall the listing (that title is then empty).

`list_displays` returns the GDI topology (`\\.\DISPLAYn`, bounds, work area, DPI, primary) plus the physical targets `QueryDisplayConfig` reports for each source, including cloned outputs (`friendlyName`, `devicePath`, EDID manufacturer/product, output technology, connector instance). `includeModes` (default false) adds, for each target, refresh rate, active width and height, rotation, scaling, the source adapter LUID, and advanced-color support, enabled state, and bits per color. Those fields are null when Windows does not report them. When the CCD API is unavailable (session 0, some RDP sessions) the tool falls back to `EnumDisplayDevices` and may return empty monitor details.

`take_screenshot` captures a PNG of the console user's desktop. `target` is `desktop` (the default; the virtual screen across all monitors), `display` (one GDI display: `display` is `primary` or `\\.\DISPLAYn` from `list_displays`), `window` (one top-level window), or `region` (`x`, `y`, `width`, `height` in the same physical-pixel coordinates `list_displays` reports; the rectangle is clipped to the virtual screen and an empty overlap fails with `empty_region`). A window is selected with `windowHandle` from `list_windows`, or with `pid` / `processName` / `titleRegex` that must resolve to exactly one visible top-level window (`ambiguous_window` lists the candidates; `window_not_found` and `window_minimized` are the other failures). Do not pass both a handle and the filter fields.

The tool returns a downscaled PNG as MCP image content (longest edge `maxEdge`, default 1920; `0` omits the preview) plus JSON metadata: target, captured bounds, full and preview sizes, DPI, intersecting displays, window handle and title when relevant, and the saved path, size and SHA-256 when `saveTo` is set, plus a `download` link to the saved file when the Files module is enabled and the path is in a root with `Read` access. With `ApiTokens` configured that link carries a one-time ticket, so fetching the full-resolution PNG does not need the API token. `saveTo` is a `root:relative\file.png` in a root with Write access; `overwrite` replaces an existing file. `includeCursor` draws the mouse pointer. The capture always runs in the interactive session through `Vestigo.exe --session-helper capture-screen`; there is no service-session path.

The MCP image block is for the model. A chat client may not show it to the person who asked. `share: true` adds a resource link and a `share` object (`url`, `expiresUtc`, `singleUse`, `instruction`) for the same downscaled preview, and the instruction says to present that URL instead of claiming the image is already visible. The URL is `GET /desktop/shares/{id}?ticket=...`. It does not use the Files module, a configured root, or `fetch_file` (`fetch_file` imports onto this host). The server keeps only that preview in memory, at most 16 previews and 32 MiB, for 10 minutes. The ticket is the only credential: an API token does not fetch the image, and the URL does not need one. One completed response consumes the ticket; a failed transfer leaves it usable. A restart drops every share. `share` with `maxEdge: 0`, or when every slot is busy and `saveTo` did not store a file, fails with `share_unavailable`. When the PNG was stored and issuing the link fails, the call still succeeds and `shareError` carries that failure; there is no share link. Use `saveTo` when the full-resolution PNG must be kept.

Known limitations: the lock screen and UAC secure desktop fail with `desktop_unavailable`; DRM or `SetWindowDisplayAffinity` windows, and some GPU or fullscreen-exclusive apps, can render black with `PrintWindow`; protected content is not bypassed. Image bytes and base64 are never logged.

### Seeing the screen: `inspect_screen` and `find_on_screen`

`inspect_screen` describes the console user's screen for an agent. It takes the same `target` selectors as `take_screenshot` and needs `Vestigo:Desktop:AllowScreenshots`. The result has two parts, so a client that cannot show images can still act on it. The image is the capture downscaled to `maxEdge` (default 1280, 320 to 3840) with numbered boxes drawn on it (green for UI Automation, blue for OCR, red for OpenCV regions). The JSON lists every box as an element: `id`, `source` (`uia`, `ocr` or `cv`), `role`, `name` (UI Automation) or `text` (OCR), `box` in pixels of the returned image, and `enabled` or `focused` when known. UI Automation walks the windows that overlap the capture and skips elements covered by windows above them; edit control values are never read, only names and roles. OCR uses `Windows.Media.Ocr` with the user's profile languages and is reported as `ocr_unavailable: ...` when no language pack is installed. OpenCV finds contour regions only where the other two report nothing, which is the only coverage for owner-drawn or game surfaces. `uia` and `ocr` (both default true) switch the sources, `imageMode` is `annotated` (default), `raw` or `none`, and `grid: true` draws a labelled coordinate grid instead of boxes.

The returned list holds at most 150 elements. UI Automation and OCR share that budget evenly, a source that finds fewer passes the rest to the other, and contour regions fill what remains. Within a source, the elements that do not fit are the lowest on the screen. An OCR line is kept when it sits inside a named container whose name does not match the line. It is dropped when a named UI Automation element covers it and the texts agree, unless a text search matches the OCR line and not that element's name. `uia` and `ocr` describe collection: `ok`, `skipped`, `truncated` (the helper stopped at its own limit), or a failure reason. `truncated`, `candidates` and `omitted` (each split into `uia`, `ocr` and `cv`) describe delivery. `candidates` counts elements that survived deduplication and overlap removal, and `omitted` counts how many of those did not fit. `truncated` is true when any were omitted. The helper still collects at most 600 UI Automation elements and 200 OCR lines, so a smaller region gives better coverage when a full desktop exceeds those limits.

Each result carries a `captureId`, valid for about two minutes (at most eight are kept). Pass it to `send_input` to click an `elementId`, or to use `x,y` in the returned image's pixels. `diffAgainst` takes an earlier `captureId` captured with the same target and `maxEdge` and adds `diff`: the percentage of changed pixels and the regions that changed, which answers "did my click do anything" without comparing images by eye. A different area or size fails with `capture_mismatch`; an unknown or expired id fails with `capture_expired`.

`find_on_screen` locates things. `text` matches UI Automation names and OCR text (case-insensitive substring) across every element the helper collected, before the 150-element cap, so a saturated UI Automation result cannot hide an OCR match. Those matches are kept first. When the matches themselves exceed 150, the response keeps the first 150 in reading order and sets `matchesTruncated` to true. `template` is a PNG or JPEG at `root:relative\file.png` under a `Read` root (at most 8 MiB), or `templateCaptureId` with `templateX`, `templateY`, `templateWidth` and `templateHeight` crops a region out of an earlier capture. Template matching is multi-scale normalized cross-correlation on the working image, so the template does not have to be at the same scale, and `minConfidence` (0.5 to 0.99, default 0.8) filters the candidates. Results are `matches` with `kind`, `elementId`, `box` and, for templates, `confidence`, plus the new `captureId`, so a match can be clicked directly. The same `truncated`, `candidates` and `omitted` fields as `inspect_screen` say whether the capture's element list was complete.

Failures use `screenshots_disabled`, `no_interactive_session`, `desktop_unavailable`, `invalid_request`, `capture_expired`, `capture_mismatch`, `vision_failed` (OpenCV could not process the image) and the helper codes `helper_failed` and `helper_timeout`.

## Input

The `Input` module is disabled by default and needs the `Desktop` module. `send_input` injects mouse and keyboard input into the console user's session, so anything that user can do with the mouse and keyboard can be done through it. Read [security.md](security.md#input) first. It is also gated by `Vestigo:Input:AllowInput`. Enabling the module and the gate without `ApiTokens` is allowed and logs a startup `SECURITY WARNING`.

`actions` run in order, in one call. `move`, `click` (`button` `left`, `right` or `middle`; `count` 1 to 3), `down`, `up`, `scroll` (`deltaY` wheel notches down, negative up; `deltaX` right), `drag` (from `x,y` to `toX,toY` with the chosen button, always released afterwards), `type` (`text`, sent as Unicode characters, so the keyboard layout does not matter; newline and tab become Enter and Tab), `key` (a key or chord such as `enter`, `ctrl+c`, `ctrl+shift+esc`, `alt+f4`, `win+r`, `f5`, `pagedown`; at most six keys) and `wait` (`milliseconds`). A point is `elementId` with `captureId`, or `x` and `y`: in the pixels of the returned image when `captureId` is set, otherwise absolute virtual-screen physical pixels (the coordinates `list_displays` reports). Click, down, up and scroll without a point act at the current mouse position. `focusWindow` takes a window handle from `list_windows`, restores it when minimized and tries to bring it to the foreground first; when Windows refuses, the result says `foreground_not_granted` and the input goes to whatever has focus. The whole list is validated and resolved before anything is sent, so a bad action injects nothing. Limits come from `Vestigo:Input:MaxActions`, `MaxWaitMilliseconds` and `MaxTypedCharacters`; an encoded batch that does not fit a command line is refused with `invalid_request`.

`observe: true` makes one call act and look: after `observeDelayMs` (default 300) the server returns a fresh `inspect_screen` result for the desktop, or for `observeWindowHandle`, with `imageMode` and `maxEdge`. It needs `Vestigo:Desktop:AllowScreenshots` and fails with `screenshots_disabled` before any input is sent when that gate is off. If the input succeeded but the observation failed, the result still reports `performed` and adds `observeError`.

The result reports `performed` (actions completed) and `sessionId`. Errors: `input_disabled`, `invalid_request`, `capture_expired`, `element_not_found`, `no_interactive_session`, `secure_desktop_active` (the input desktop is not the session's default desktop: a UAC prompt, the lock screen or Ctrl+Alt+Del), `uipi_blocked`, `input_failed`, `window_not_found`, `helper_failed` and `helper_timeout`. When an action fails midway, the message says how many actions ran first. Typed text is never logged; only action kinds and counts are.

Known limitations: input cannot reach the secure desktop or send the secure attention sequence (Ctrl+Alt+Del). Windows blocks input into elevated windows from a non-elevated process (User Interface Privilege Isolation), so use `elevated: true` for those; Windows may still drop such input without an error. Some games and remote-desktop clients read raw input and ignore injected events.

## Audio

The `Audio` module is disabled by default. It lists Core Audio playback (`render`) and recording (`capture`) endpoints and can switch the default device. Endpoint names and the processes using them are information disclosure; changing the default device is a separate gate. Read [security.md](security.md#audio) first. Enabling the module without `ApiTokens` is allowed and logs a startup `SECURITY WARNING`.

`list_audio_endpoints` returns each matching endpoint's id, friendly name, device description, interface name, flow, state, form factor, the default roles it currently holds (`console`, `multimedia`, `communications`), master volume percent, mute, per-channel volumes, a short peak-meter sample (`PeakPercent`), whether playback or recording looks active, and the audio sessions on that endpoint (`processId`, `processName`, `displayName`, session state, `isSystemSounds`). `Active` is true when any session is in the Core Audio active state or the sampled peak is above zero. Volume, mute, peak, and sessions are omitted (null or empty) when the endpoint does not expose them.

Filters: `flow` is `all` (default), `render`, or `capture`. `state` is `active` (default) or `all` (includes disabled, unplugged, and not-present). `id` returns one endpoint. `includeSessions` defaults to true. Peak sampling lasts `Vestigo:Audio:MeterSampleMilliseconds` (0 disables it). Audio sessions belong to a logon session, so the default `interactive` context starts `Vestigo.exe --session-helper list-audio` in the console user's session. `context: service` enumerates in-process and does not see user-session playback or recording.

`set_default_audio_endpoint` sets the default for the endpoint's flow. `role` `default` is Windows' Default Device (console and multimedia). `communications` is the Default Communication Device. `all` sets both. It is refused with `set_default_disabled` unless `Vestigo:Audio:AllowSetDefault` is `true`. The endpoint must exist and be active (`not_found`, `not_active`). The result includes the applied roles and a refreshed listing of that flow so the new `defaultFor` flags can be confirmed. Switching uses the undocumented `IPolicyConfig` interface and can fail with `set_default_failed` if that contract is unavailable. Per-app device overrides from Settings are neither shown nor changed.

## Remote debugger

The `RemoteDebugger` module is disabled by default and requires the `Jobs` and `Processes` modules. Enabling those without `ApiTokens` logs a startup `SECURITY WARNING`. It manages the Visual Studio Remote Debugging Tools (`msvsmon.exe`) for Visual Studio 2022 (17) and 2026 (18). A running monitor lets a remote debugger run code on this machine; read [security.md](security.md#remote-debugger) first.

Workflow: `get_remote_debugger_status` (is it installed?) -> `install_remote_debugger` (job) -> optionally `prepare_remote_debugger_computer` (firewall) -> `start_remote_debugger` -> connect Visual Studio (Debug > Attach to Process, connection target `host:4026`) -> `stop_remote_debugger`.

Every tool takes `version` (`2022` or `2026`) and `arch` (`x64` default, `arm64`, `x86`).

`get_remote_debugger_status` lists every version and architecture with the discovered `msvsmon.exe` path, how it was found (`standalone`, `ide`, `vswhere`, `registry`, `extra`), its file version and the installer URL, plus each running `msvsmon.exe` with pid, session id, port, whether that port is listening and whether Vestigo started it. The port comes from the process command line (read through CIM) and falls back to the port Vestigo used or the default.

`install_remote_debugger` downloads `https://aka.ms/vs/<17|18>/release/RemoteTools.<amd64|arm64|x86>ret.enu.exe` to a temporary directory under the spool, requires a valid Authenticode signature (`WinVerifyTrust`) whose signer CN or O is `Microsoft Corporation`, and runs it as the service account with `/install /quiet /norestart`. Everything happens inside a job so the call returns a job id at once; the temporary files are removed at the end. It returns `Skipped` when `msvsmon.exe` is already found, unless `force` is true. `Vestigo:RemoteDebugger:InstallerDownloadTimeout` limits the download.

`start_remote_debugger` runs `msvsmon.exe /nostatus /silent /nofirewallwarn /port <port> /timeout <seconds>` in the `interactive` context by default (`elevated` uses the user's linked administrator token). `port` defaults to `Vestigo:RemoteDebugger:DefaultPort` (4026); `timeoutSeconds` (30 to 86400, default 3600) is how long the monitor waits without a connection. `auth` is `windows` (default; `allowUsers` entries become `/allow`) or `none` (`/noauth /anyuser`), which needs `iUnderstandNoAuthIsInsecure: true` and adds a warning to the result and the log. A second instance on a port that is in use is refused with `port_in_use`. The result has the pid, port, the sanitised arguments, whether the port is listening, and the job id.

`stop_remote_debugger` takes a `pid` of a running `msvsmon.exe` or `all: true` for the instances Vestigo started. It posts a close request, waits `gracefulTimeoutSeconds`, then kills the process tree.

`prepare_remote_debugger_computer` runs `msvsmon.exe /prepcomputer /private /quiet` as a job (default `service` context) to configure firewall rules and permissions for private networks.

## Devices

The `Devices` module changes drivers and device state. Mutating operations need the elevated service account; the query tools are read-only and mostly work without elevation. Drivers run in the kernel: installing one is arbitrary code execution at the highest privilege. That is the purpose of the module, so enable it only on machines you intend to debug drivers on (`Vestigo:Modules:Devices:Enabled`), and protect `/mcp` with an API token whenever more than one client can reach it.

Driver actions go through the bundled nefcon CLI with fixed arguments (see `INefconRunner`). Every result has `exitCode`, `outputTail` and `rebootRequired`, plus `timedOut`. Exit code `0` is success and `3010` is success that needs a restart (`rebootRequired: true`). Any other exit code returns `success: false` with error code `nefcon_failed` and the same result in `value`; exit code `1` normally means the service is not elevated or nefcon rejected an argument. A run longer than `Vestigo:Devices:NefconTimeout` is killed (`nefcon_timeout`). Calls run one at a time. A reboot is never triggered by Vestigo; apply it yourself when `rebootRequired` is true.

INF paths (`install_driver`, `uninstall_driver`, `install_filter_driver`, `uninstall_filter_driver`, `inf_default_install`, `inf_default_uninstall`) must be existing `.inf` files inside a root with `Read` access, as `name:relative\path` or an absolute path. The driver's other files are read by Windows from beside the INF, so give the root the whole driver package directory.

| Tool | Purpose |
| --- | --- |
| `create_device_node` | Create a ROOT device node (`className`, `classGuid`, `hardwareId`, optional `noDuplicates`). |
| `remove_device_node` | Remove a node by `hardwareId` and `classGuid`. |
| `install_driver` | Without `hardwareId`: install the package. With it: create the ROOT node and install the driver on it; `noDuplicates` and `removeDuplicates` (which needs `noDuplicates`) only apply with a hardware ID. |
| `uninstall_driver` | Uninstall the driver described by an INF. |
| `install_filter_driver` | Install a filter driver INF and register its class filter. |
| `uninstall_filter_driver` | Remove the class filter and service (`classGuid`, `serviceName`, `position` upper or lower). With `infPath` the driver store package is purged too; `allVersions` (needs `infPath`) purges every version. |
| `add_class_filter`, `remove_class_filter` | Edit a class's upper or lower filter list for an existing service. |
| `inf_default_install`, `inf_default_uninstall` | Run `[DefaultInstall]` or `[DefaultUninstall]` of an INF. |
| `remove_driver_store_package` | Remove driver store packages by original INF name (for example `mydriver.inf`), optionally narrowed by `classGuid` and `serviceName`. nefcon has no all-versions switch for this command, so it removes what the name and filters match. |
| `restart_device`, `enable_device`, `disable_device` | Change state by instance ID (for example `ROOT\SYSTEM\0001`). |
| `find_devices_by_interface` | Instance IDs and device paths exposing an interface GUID (at most 256; `truncated` tells if the cap was hit; `presentOnly` false includes phantom devices). |
| `find_devices_by_hardware_id` | Instance IDs in a device class whose hardware IDs match (`presentOnly`, `allowPartial`). |
| `find_devices` | Enumerate device nodes with optional AND filters `nameContains` (description substring), `hardwareId` (exact, or prefix with a trailing `*`), `deviceClass` (class name or GUID), `presentOnly` (default true) and `limit` (default 100, max 500). Returns `devices`, `total` and `truncated`. |
| `get_device` | Details of one device by `instanceId`: hardware and compatible IDs, class, service, present flag, `problemCode` (0 is healthy), `devNodeStatus` and driver key, description, provider, version, date and INF. Properties a device lacks are null. |
| `get_class_filters` | Upper and lower filter driver service names registered for a `classGuid` (registry read, no elevation needed). |
| `list_driver_store` | Driver store packages with `nameContains` (published or original INF), `provider`, `deviceClass` (name or GUID), `includeInbox` (default false) and `limit` (default 100, max 500); each has published name, original INF, provider, class, version, date, architecture and bound device instance IDs. |

Class GUIDs may be written with or without braces and must not be empty. Instance IDs must contain a `\`, and no value may be empty, start with `-`, or contain control characters. Device state tools map library failures to stable error codes: `device_not_found`, `config_manager_failed`, `win32_failed`, `windows_required` and `device_operation_failed`.

The query tools (`find_devices`, `get_device`, `get_class_filters`, `list_driver_store`) run in-process through Nefarius.Utilities.DeviceManagement 6.2.0 and never start nefcon. They are read-only and mostly work without elevation, though some device properties or driver store details may be missing for an unprivileged service account.

### Typical driver development workflows

Bring up a root-enumerated driver:

1. `create_device_node` with the class name, class GUID and a hardware ID such as `Root\MyDriver`. (`install_driver` with a `hardwareId` does this and the install in one step.)
2. `install_driver` with the INF root path and the same `hardwareId`.
3. If the driver needs a filter on a class: `install_filter_driver`, or `add_class_filter` when the service already exists.
4. `find_devices_by_hardware_id` to get the instance ID, then `restart_device` so the stack is rebuilt with the new driver or filter. Do a reboot instead when `rebootRequired` is true.

Iterate on a new build: `install_driver` again with the same hardware ID and `noDuplicates`, then `restart_device`.

Tear down: `uninstall_filter_driver` (with `infPath` to purge its package) or `remove_class_filter`, then `uninstall_driver`, `remove_device_node`, and finally `remove_driver_store_package` with the INF name so old packages do not accumulate in the driver store.


## Windows servicing

The opt-in `WindowsServicing` module requires Jobs and is separate from Vestigo's
`Updates` self-updater. All eleven tools advertise read-only, non-destructive metadata.

`get_reboot_pending` combines registry and WUA signals as pending, notPending or
unknown. `list_pending_file_operations` reads both Session Manager queues with raw
paths, normalized DOS/UNC paths where recognized, replacement markers and malformed
pair warnings; it never opens or changes the queued files.

`list_windows_updates` starts an offline-only WUA applicability job;
`get_update_history` returns a bounded newest-first history window with HRESULTs;
`get_windows_update_status` snapshots WUA state and relevant services. Stopped
trigger-start services are not automatically blockers. `get_servicing_status`
reads CBS/pending-file metadata without a health scan; `list_servicing_packages`
starts a DISM API inventory job. Read job output as paged JSON using Jobs tools.

`get_update_failure_details` collects bounded history, events and log evidence;
`get_servicing_logs` tails fixed CBS/DISM logs through Read roots.
`get_update_storage_status` reports Windows-volume space and fixed-file metadata,
without recursive cache totals or a WinSxS allocation estimate. `get_file_lockers`
uses Restart Manager for one file inside a Read root without stopping processes.

Native diagnostics share one concurrency slot. Timeout or cancellation stops
waiting, and the slot remains held until Windows returns. See
[Windows servicing diagnostics](windows-servicing.md) for exact sources, caps,
job semantics, data disclosure and limitations. No install, repair, online scan,
queue cancellation, cache reset or reboot operations are exposed.
