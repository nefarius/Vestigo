# Security

Vestigo binds to one IP address and runs as a Windows service so realtime ETW session creation can be elevated. That privilege is local administrator or `SeSystemProfilePrivilege`. The configuration default is loopback (`127.0.0.1`); a fresh MSI install defaults to any address with a generated token.

When `ApiTokens` is empty, `/mcp` accepts anonymous clients. That is the `dotnet run` default and the MSI localhost-no-token mode. A fresh MSI install defaults to any address with a generated token. Add one or more tokens to require `Authorization: Bearer <token>`. Comparison uses SHA-256 digests and a fixed-time check. Tokens are not logged and are not copied into claims.

`/` is an anonymous static page that explains how to connect an MCP client. It does not report the version, enabled modules, roots, or whether tokens are configured. `/health` stays anonymous so a local supervisor can probe the process without a token. A missing or invalid token receives HTTP 401 and `WWW-Authenticate: Bearer`.

Trace ETL, PDB, TMF, zip, and conversion-output paths are canonicalized, including existing directory links, and must stay inside the effective `AllowedInputRoots` or `AllowedOutputRoots` (the built-in `<settings>\traces` folder when a list is empty). A root of `D:\traces` does not allow `D:\traces-extra` or a link that resolves outside that root. The accepted path is the resolved location, so a later open uses that path instead of reopening the original link. Validation and later opens are not atomic if a path component changes. Unsupported extensions are rejected. Existing outputs are kept unless `overwrite` is true. Input size, event count, output size, archive entry count, archive compression ratio, and capture lifetime are capped. PDB files under the resolved symbol cache (the environment-selected cache when `_NT_SYMBOL_PATH` chooses one) may be passed to Trace tools. `extract_trace_archive` refuses zip-slip (`..`, absolute paths, drive letters, alternate data streams) and will not write through links. `resolve_binary_symbols` reads binaries through Files roots (`Read`), not through the trace lists.

File, log, event-log, process, and device paths, and `take_screenshot`'s `saveTo` output path, use named `Vestigo:Roots` with the same link-following canonicalization and `Read`, `Write`, or `Execute` flags. `Vestigo:VolumeRoots` can add whole lettered volumes as `drive-c`, `drive-d`, and so on, merged with any hand-written `Roots`. `VolumeRootAccess` applies to every generated volume root. Write or Execute on a whole volume lets a client replace drivers, services, and scripts; Vestigo logs a startup `SECURITY WARNING` in that case. Explicit process paths need a root with `Execute` access. A bare process name may be resolved from the service `PATH` without named-root or `PathPolicy` checks when `Processes:AllowPathLookup` is enabled. Those roots are independent of the trace input and output lists.

`attach_etw_session` exposes another session's machine-wide trace data to API clients, so it is disabled until `Vestigo:AttachableSessions` lists the sessions that may be read. Attaching is read-only and Vestigo-owned sessions cannot be attached.

`Kestrel:Endpoints` is rejected at startup. The process binds only `Vestigo:ListenAddress` and `Vestigo:ListenPort`. IPv6 addresses are formatted with brackets.

## Network exposure

`ListenAddress` accepts any IP address, including `0.0.0.0` and `::`. Vestigo does not require a token, because a localhost-only install without one is a supported setup. The risk grows when the address is not loopback and `ApiTokens` is empty: anyone who can reach the port can use every enabled module, including captures, files, services, environment changes, and any opt-in administrator-equivalent tools. For that reason:

- Configure `ApiTokens` (strongly recommended) whenever `ListenAddress` is not loopback. Use long random values, for example 32 random bytes encoded as base64url.
- At startup Vestigo logs a prominent `SECURITY WARNING` when the address is non-loopback and `ApiTokens` is empty. The warning never contains token values.
- Traffic is plain HTTP. Tokens and traces cross the network unencrypted, so use a trusted network or a TLS-terminating proxy.
- Open the Windows firewall only for the chosen port and, where possible, restrict the rule's remote addresses.

The MSI installer first asks where the server listens (localhost or any address) and then whether to require an API token. Any address without a token shows a warning; any address with a token is the default. Two later pages choose the file-system volume set (`VolumeRoots`) and the access granted to those volumes (`VolumeRootAccess`). The default is local fixed disks with Read, Write, and Execute. Custom `Roots` already in the settings file are kept and merged. The choice is written to `%ProgramData%\Nefarius Software Solutions\Vestigo\appsettings.json`, readable only by SYSTEM and Administrators, so the token is stored there in clear text. Modes that bind any address add an inbound TCP firewall rule for the port; uninstalling removes it. The page after the volume choices is a feature tree that selects the modules (see [windows-service.md](windows-service.md#modules)); any listen mode can be combined with any module. Screenshots are a separate unchecked child of Desktop (`DesktopScreenshots` writes `Vestigo:Desktop:AllowScreenshots`). Silent self-update is a separate unchecked child of Updates (`SelfUpdate` writes `Vestigo:Updates:AllowSelfUpdate`). That includes any address, no token, with `Processes` and software uninstall: it is a supported choice for an isolated lab network, and anyone who can reach the port is then administrator-equivalent. The server never refuses this combination; it logs a startup `SECURITY WARNING` that names the enabled administrator-equivalent capabilities. See [windows-service.md](windows-service.md) for the silent-install properties.

The `Services` module can stop and reconfigure system services, so mutating tools (`start_service`, `stop_service`, `restart_service`, `set_service_start_type`, `create_driver_service`, `delete_service`) refuse every name in `Vestigo:Services:ProtectedNames` (case-insensitive; default `Vestigo`, `RpcSs`, `DcomLaunch`, `PlugPlay`, `Power`, `LSM`, `SamSs`), including dependents that `stopDependents` would stop. Configured names are added to the defaults, so the defaults cannot be removed through configuration. Service names are validated against a restricted character set and never passed as paths. `create_driver_service` resolves the driver binary through `RootPolicy` with `Execute` access, requires an existing `.sys` file, and passes the resolved full path to nefcon; `delete_service` only accepts names of `KERNEL_DRIVER` services. Read-only tools are not restricted by the protected list. Other services can still be stopped by any client that is allowed to call `/mcp`, so keep API tokens enabled on shared machines.

`set_environment_variable` with machine scope is a machine-wide configuration change that affects every process started afterwards, so treat access to `/mcp` as administrative when the module is enabled; disable it with `Vestigo:Modules:Environment:Enabled=false`. `Vestigo:Environment:ProtectedNames` (default `COMSPEC`, `SystemRoot`, `windir`) lists names that cannot be set or unset in any scope. Variable values are never written to the Vestigo log, and `set_environment_variable` does not echo the value. User scope needs the SYSTEM account (`SeTcbPrivilege`) to obtain the console user token and fails with `user_not_available` and a `reason` when nobody is logged on. Process scope changes only the Vestigo service process and its children.

The Registry module is opt-in. When it is enabled, a client can read values under the allowed prefixes, including service parameters and policy keys. Values are returned to the caller and are not written to the Vestigo log. `HKLM\SAM`, `HKLM\SECURITY`, `HKLM\SYSTEM\CurrentControlSet\Control\Lsa`, and `HKLM\SOFTWARE\Microsoft\Windows NT\CurrentVersion\Winlogon` stay denied so credential material and an automatic-logon password are not read by a broad prefix. Configured deny entries are added to that list and cannot replace it. A registry symbolic link is followed by Windows and is not a second confinement check. Enabling the module without `ApiTokens` logs a startup `SECURITY WARNING`.

`read_json_path` and `get_json_summary` disclose JSON document content the same way `tail_text_file` discloses text. A status or configuration file can contain a user name, a serial, or a token. The tools log neither the document nor a matched value; a log line may contain the root path, the query, and the error code. The returned SHA-256 covers the whole file, not the matched value. The result is inline data and does not mint a download ticket. The file is opened with `FileShare.ReadWrite | FileShare.Delete` after its length is checked, so an oversized document is refused before it is read.

Event log channels such as `Security` are limited by Windows access control for the service account; `.evtx` files and text files for `tail_text_file` must lie inside a configured root with `Read` access. Log and event content is returned to the client as data and can contain sensitive information. Text files are opened with `FileShare.ReadWrite | FileShare.Delete` so they can be read while another process writes them.

`search_text` discloses file content like `tail_text_file`, but across a whole directory tree, so a client can sweep every file under a `Read` root for a pattern in one call; grant `Read` only on trees you are willing to expose. The path is resolved through the same root check first, and ripgrep is started with `--no-follow`, so links and junctions inside a root cannot lead outside it. ripgrep is bundled, not downloaded at run time: the build pins ripgrep 15.2.0 by URL and SHA-256 (`build/RipgrepPin.cs`, archive and `rg.exe`), the binary is not Authenticode-signed, and Vestigo re-checks the digest before every launch unless `Vestigo:Logs:RipgrepSha256` is empty for an administrator-overridden path. Arguments are a fixed list with no shell: the pattern follows `-e`, each glob is attached as `--glob=<value>`, the path follows `--`, and `--no-config` ignores any ripgrep configuration file. Clients cannot pass `--pre` or any other flag. Patterns and globs are length-limited and cannot contain line breaks; regular expressions run in ripgrep's linear-time engine (PCRE2 look-around is not enabled). Each search is bounded by result, line-length, time and concurrency limits, and the process tree is killed when a limit or the request ends. Matched content is returned as data and can contain sensitive information.

Spools, logs, the symbol cache, the built-in `traces` folder, and owned-session state are stored under ProgramData, outside the install directory. The MSI creates `%ProgramData%\Nefarius Software Solutions\Vestigo`, `logs`, `spool`, `symcache` and `traces` with a protected DACL (inheritance disabled) that grants only SYSTEM and Administrators full control, and fails the install when any of them is a reparse point. The `Nefarius Software Solutions` folder itself is given that protected ACL plus ReadAndExecute for Users on the folder only, and an untrusted owner is replaced.

`Vestigo:SymbolServerAuth` stores the symbol-server secret in the same machine settings file as `ApiTokens` (readable only by SYSTEM and Administrators) or in a `SecretFile` you provision. The secret is never logged and is never returned by `get_trace_settings`. Credentials are added only on requests to the configured `SymbolServer` origin (scheme, host, and port). Vestigo follows at most five redirects itself and drops credentials when the origin changes, so an `X-Api-Key` or `Authorization` header is not forwarded to blob storage. Authentication requires HTTPS except when the server is loopback. A `user:pass@` prefix on `SymbolServer` is converted to Basic and stripped so it cannot appear in diagnostics.

At startup the service verifies the same tree and fails closed: it refuses to start when the settings path or any directory in the tree is a reparse point (symlink or junction), when an existing directory has an untrusted owner (checked for the five tree directories at startup, for every existing component whenever a spool directory is created, and for every entry before its ACL is reset during a repair), or when a parent directory above the settings directory can be deleted or re-ACLed by an untrusted principal. A trusted-owner directory with a permissive or inherited ACL is reset to the protected ACL (children revert to inheriting it) and a warning is logged. Because only SYSTEM and Administrators can alter the tree, a lower-privileged user cannot swap a path component for a link between a check and its use. Every spool consumer (captures, jobs, the session helper, the Remote Debugger installer download, uninstall logs) creates its directory through the same check, and the Remote Debugger re-checks right before running the downloaded installer. `VESTIGO_SETTINGS_DIR` skips only the parent-directory ACL check. A `Vestigo:SymbolCache` set outside the settings tree is not verified. Allow write access for the trusted identity that runs Vestigo (the configured MSI service account, or the user running `dotnet run`). Do not share a writable cache between a privileged service and an untrusted user.

The MSI `Automatic updates` feature still ships the packaged Vicius 1.20.1 executable. Its scheduled and logon checks, and the MCP `start_self_update` tool, use that binary. The shipped `Nefarius_Vestigo_Updater.json` is authoritative and points only at `https://buildbot.nefarius.at/builds/Vestigo/latest/updates.json`. Vicius verifies `updates.json.minisig` with its embedded Nefarius minisign public key before parsing the manifest. The signed manifest carries the MSI size, lowercase SHA-256, and publisher pin. Vicius then requires a valid Authenticode chain whose simple subject name is `Nefarius Software Solutions e.U.`

When installed, the configuration and updater live under Program Files, so a non-administrator cannot retarget the feed. The stock updater binary also contains a Nefarius API address used only when that local configuration is absent. Rotating the minisign key requires a newer official Vicius build with the new public key compiled in; renewing the Authenticode certificate does not, while its subject name stays the same. The minisign private key is a release secret and is not stored in the repository or in build artifacts.

## Updates

`check_for_updates` is an outbound HTTPS request from the service account to `https://buildbot.nefarius.at/builds/Vestigo/latest/`. Vestigo verifies `updates.json.minisig` with the same Nefarius minisign public key that Vicius embeds, then refuses any URL that is not under that Buildbot directory. The check uses the service account's proxy settings. The module is on by default; disable it with `Vestigo:Modules:Updates:Enabled=false` if the host should not contact Buildbot.

`start_self_update` stays off until `Vestigo:Updates:AllowSelfUpdate` is `true`. It can only launch the packaged updater after `ExecutableTrust` accepts the file, and that updater can only install the signed release the verified manifest describes. Treat a token that can call it as administrator-equivalent: the MSI stops and restarts the Vestigo service, which ends in-flight work and drops the MCP session. Enabling the option without an entry in `ApiTokens` only logs a `SECURITY WARNING` that names "Self-update". The installer does not register Vicius autostart or the daily task when the installing user is SYSTEM, so a service-triggered upgrade cannot leave a SYSTEM scheduled task behind.

Clients should never need the API token to move files. When `ApiTokens` is set, tools that prepare a transfer (`get_download_url`, `get_upload_url`, `take_screenshot` with `saveTo`, `convert_etl`) mint a ticket in the URL they return. A ticket is a random 256-bit value, stored only as a SHA-256 digest in memory, bound to one method and one resolved path (and the upload flags), expires after `Vestigo:Files:TicketLifetime` (default 15 minutes, at most 24 hours), and is consumed by the first successful transfer; concurrent reuse is refused while a transfer is in flight. Roots are re-checked on every request, so a ticket never widens access. It still grants whatever that one transfer allows to whoever holds the URL, and it is carried in the query string over plain HTTP, so treat the URL as a secret until used. The API token keeps working for permanent access. Named roots (`Vestigo:Roots`) and any `VolumeRoots` gate the file tools and the `/files` endpoints. A root needs `Write` access before anything can be uploaded, copied in, moved, deleted or replaced there, and `Read` for downloads and listings. Uploads are executable-capable data: a client with `Write` access to a root that holds drivers, services or scripts can change what runs on the machine, and a service running as administrator makes that a privilege boundary. Whole-volume roots with Write or Execute are the same privilege boundary for every file on that volume. Grant `Write` only to roots that need it, and use API tokens whenever the endpoint is reachable by more than one local user. Uploads are bounded by `Vestigo:Files:MaxUploadBytes`, written to a temporary file next to the target and committed only after the optional SHA-256 matches. The `/files` endpoints reject `:` in paths to block NTFS alternate data streams, and a root, or a directory containing a root, cannot be deleted or moved. `fetch_file` can read UNC paths with the service account's identity, so restrict who may call it. Scheduling reboot-time deletes or replacements needs administrator rights; locked-file replacement leaves a `.vestigo-old-*` file until it can be removed.

nefcon (the device and driver CLI used by `Vestigo.Devices`) is bundled, not downloaded at run time. The build pins nefcon 1.21.0 by archive URL and SHA-256 (`build/NefconPin.cs`), extracts only `x64\nefconc.exe`, and requires a valid Authenticode signature whose simple subject name is `Nefarius Software Solutions e.U.` before the MSI installs it under `tools\` in Program Files. The runner only executes that file (or an absolute `Vestigo:Devices:NefconPath` set by an administrator), passes arguments as a discrete list with no shell, rejects values that start with `-`, and never accepts free-form arguments. The runner does not confine file paths itself; code that exposes it must apply `RootPolicy` first.

## Processes

`run_process`, `close_app` and `kill_process` execute and terminate arbitrary programs. This is by design: a client that can call them can run any program under the `Execute` roots, or any program on `PATH` while `AllowPathLookup` is true, as the service account (normally SYSTEM) or as the console user. Treat an API token for this module as administrator-equivalent. The module is off by default. Enabling it with `Vestigo:Modules:Processes:Enabled = true` requires the `Jobs` module (startup fails otherwise). Without an `ApiTokens` entry it still starts and logs a `SECURITY WARNING`; use that only on a network you trust.

Controls that do apply: programs must be files inside a root that has the `Execute` flag, using the same link-following canonicalization as other paths; working directories need `Read`; bare names are limited to executables found on the absolute entries of the service `PATH` (never the current directory) and can be turned off with `AllowPathLookup = false`; scripts must live under an `Execute` root. Environment overrides and arguments are bounded and checked for NUL characters. `kill_process` refuses the Vestigo process, pid 0 and pid 4. `close_app` only posts `WM_CLOSE` and never kills.

The interactive context needs the service to run as SYSTEM (for `WTSQueryUserToken`). The process runs as the logged-on user on the visible desktop, and `elevated` uses that user's own linked administrator token; it never grants rights the user does not have. Job output files hold the process output and are readable through `read_job_output` until `JobRetention` expires, so do not run commands that print secrets. The session helper only accepts `close-window`, `list-windows`, `list-displays`, `inspect-window`, `window-events`, `place-window`, `restore-window`, `snapshot-display-layout`, `apply-display-layout`, `list-audio`, `set-default-audio`, `capture-screen`, `inspect-screen`, `send-input`, `probe-capture`, and `probe-audio-format` arguments. `set_default_audio_endpoint` is refused by the service unless `Vestigo:Audio:AllowSetDefault` is true; `take_screenshot`, `inspect_screen` and `find_on_screen` are refused unless `Vestigo:Desktop:AllowScreenshots` is true; `set_window_client_rect` and `restore_window_placement` are refused unless `Vestigo:Desktop:AllowWindowPlacement` is true; display-layout changes are refused unless `Vestigo:Desktop:AllowDisplayLayoutChanges` is true; `send_input` is refused unless `Vestigo:Input:AllowInput` is true; the helper does not read settings (they include API tokens). The helper does no network access.

## Desktop

`list_windows` and `list_displays` are read-only but they expose window titles, process names, and the display layout of the console user's desktop. That is information disclosure by design. `inspect_window` adds styles, DPI, integrity level, elevation and whether the process token is LocalSystem, for one window. `start_window_event_capture` records later window titles and positions for a selected process or window. Those captures are observational: they do not change focus, placement, visibility or process lifetime. `take_screenshot` additionally returns whatever is on that screen (or in one window or rectangle). The module is off by default. Screenshots stay off until `Vestigo:Desktop:AllowScreenshots` is `true`. Window placement stays off until `Vestigo:Desktop:AllowWindowPlacement` is `true`. Display-layout changes stay off until `Vestigo:Desktop:AllowDisplayLayoutChanges` is `true`. The MSI exposes each gate as an unchecked child feature of Desktop. Enabling the module with `Vestigo:Modules:Desktop:Enabled = true` does not require other modules. Without an `ApiTokens` entry it still starts and logs a `SECURITY WARNING`; use that only on a network you trust.

`set_window_client_rect` moves a window in the selected session. The move uses `SWP_NOACTIVATE` and does not change Z-order. `restore_window_placement` uses `SetWindowPlacement`, which Windows may use to activate the window. Saved placement tokens are in memory only. `start_display_layout_transaction` changes the console user's active display topology. The default is temporary, but restore writes the original topology back to the display database so a test layout cannot return at logoff. `persistent: true` also saves the test layout. Vestigo cannot stop another program, or the user, from changing the displays while a transaction is open. A client disconnect does not restore the layout; the lease does. The tools do not create or remove virtual displays, and they do not apply a vendor virtual-display policy.

The interactive context needs the service to run as SYSTEM (for `WTSQueryUserToken`) and a logged-on console user. The helper enumerates that session's desktop, or captures it, and writes JSON to a spool file under ProgramData; screenshot pixels travel as base64 in that JSON so the console user never writes into service-owned directories. The helper does no network access. `context: service` only sees session 0 and cannot take screenshots of the user's desktop. Secure and locked desktops are not enumerated or captured (`desktop_unavailable`). `elevated` uses the user's linked administrator token and is not required to read ordinary windows; `ProcessPath` may still be null for protected processes. Image bytes and base64 are never written to the service log.

`take_screenshot` with `share: true` keeps the downscaled preview in the service process and publishes `GET /desktop/shares/{id}?ticket=...`. The link is the secret. It is single-use, expires after 10 minutes, is not written to disk, and is dropped on restart. The response is `image/png` with `Cache-Control: no-store`. An API token does not authorize that URL, and the URL does not require one, so anyone who receives it can view that preview until it is used or expires. The full-resolution capture is not stored there; `saveTo` remains the durable copy and uses the Files ticket rules. The store holds at most 16 previews and 32 MiB. Treat a share URL like a screenshot.

## Input

`send_input` is the most direct way a client can act as the console user: it moves the mouse, clicks, scrolls, types and presses key chords in that user's session. Whatever the user can do on screen it can do, including approving prompts, sending messages, running programs through the Start menu or `win+r`, and, when an elevated window is in front and `elevated` is true, acting with administrator rights. Treat `Vestigo:Input:AllowInput` as administrator-equivalent. The module is off by default, depends on Desktop, and the action itself stays off until `Vestigo:Input:AllowInput` is `true`; the MSI exposes that gate as an unchecked child feature of Input. Without an `ApiTokens` entry the module still starts and logs a `SECURITY WARNING` naming input injection; use that only on a network you trust.

Controls that do apply: the whole action list is validated before anything is sent, with caps on actions, total wait time and typed characters (`Vestigo:Input:*`). Injection needs the service to run as SYSTEM and a logged-on console user, and the helper only runs `SendInput` after checking that the input desktop is the session's default desktop, so it cannot type into a UAC prompt or the lock screen and it cannot send Ctrl+Alt+Del. Windows User Interface Privilege Isolation stops input reaching elevated windows from a non-elevated helper; `elevated` uses the user's own linked administrator token and never grants rights the user does not have. The session helper accepts a batch only as a base64 JSON command-line argument, does no network access and does not read settings. Vestigo's own log never contains typed text, key chords or coordinates, only action kinds and counts. Because the batch travels on the helper's command line, Windows process-creation auditing (event 4688 with command-line logging enabled) can record it, including typed text, so do not type secrets through `send_input` on machines that audit command lines. `observe` returns screen content and so also needs `Vestigo:Desktop:AllowScreenshots`.

`inspect_screen` and `find_on_screen` are covered by the screenshot gate. They disclose what `take_screenshot` discloses and more: UI Automation names and OCR text from other applications arrive as plain text, which is easier to exfiltrate than pixels. Edit control values (passwords and typed text) are never read through UI Automation, but anything visible on screen can still be read back through OCR. A `captureId` is not a credential and is not bound to a client: it refers to a short-lived server-side copy of a capture (at most eight, about two minutes, held in memory by the service and not written to disk by the cache), so any client that can call the tools can reuse it. Template files for `find_on_screen` are read from `Read` roots with the usual link-following checks.

## Audio

`list_audio_endpoints` is read-only but it exposes device names and the processes that are playing or recording in the console user's session. That is information disclosure by design. The module is off by default. Enabling it with `Vestigo:Modules:Audio:Enabled = true` does not require other modules. Without an `ApiTokens` entry it still starts and logs a `SECURITY WARNING`; use that only on a network you trust.

`set_default_audio_endpoint` changes the user's default playback or recording device (and optionally the communications device). It is off until `Vestigo:Audio:AllowSetDefault` is `true`. The switch uses the undocumented `IPolicyConfig` COM interface; treat a token that can call it as able to redirect system audio. Per-app device overrides from Settings are not changed.

The interactive context needs the service to run as SYSTEM and a logged-on console user. The helper enumerates or switches devices in that session and writes JSON to a spool file under ProgramData. `context: service` runs in session 0 and does not see user audio sessions.

## Software

`list_installed_software` and `get_installed_software` only read the registry. `uninstall_software` runs vendor uninstallers as the service account (normally SYSTEM), so treat a token that can call it as administrator-equivalent. It is off until `Vestigo:Software:AllowUninstall` is `true`, and enabling it without an entry in `ApiTokens` only logs a `SECURITY WARNING`. The Software module depends on `Jobs`.

Controls: uninstall strings are split into an executable and an argument list and run through CliWrap with no shell; the executable must be an existing absolute path (MSI uses `msiexec.exe` from the system directory). Unknown installer types are refused rather than run interactively. The uninstaller must sit on a fixed local drive with no reparse points, and its file, directory and every ancestor must be owned and writable only by SYSTEM, Administrators or TrustedInstaller; otherwise `untrusted_executable` is returned (fail closed, also when permissions cannot be read), because a lower-privileged user could otherwise replace the file and have it run as SYSTEM. The check runs when the plan is made and again at launch. `NoRemove` and system-component entries, per-user entries (a SYSTEM uninstaller would act on the wrong profile) and display names matching `ProtectedNames` are refused. Runs are bounded by `MaxUninstallDuration` and the job output limits; the process tree is killed on timeout or cancel. Uninstaller output and MSI logs are readable through `read_job_output` until `JobRetention` expires.

## Scheduled tasks

`list_scheduled_tasks`, `get_scheduled_task` and `get_scheduled_task_history` only read. They disclose task names, authors, principals, action command lines, and the full definition XML, which can contain credentials or tokens passed as arguments, plus run history from the Task Scheduler Operational log. The module is on by default; disable it with `Vestigo:Modules:ScheduledTasks:Enabled=false` if that inventory should not leave the machine.

`run_scheduled_task`, `stop_scheduled_task`, `enable_scheduled_task`, `disable_scheduled_task` and `delete_scheduled_task` stay off until `Vestigo:ScheduledTasks:AllowChanges` is `true`. Running a task executes its actions as the task's principal, often SYSTEM, so treat a token that can call it as administrator-equivalent. Enabling the option without an entry in `ApiTokens` only logs a `SECURITY WARNING` that names "Scheduled task changes". `delete_scheduled_task` and `disable_scheduled_task` refuse task paths under `Vestigo:ScheduledTasks:ProtectedPaths` (default `\Microsoft\Windows\`, case-insensitive prefixes; configured entries are added to the default). Vestigo never creates or edits task definitions, so it cannot plant new actions.
## System

`get_system_info`, `get_boot_state`, `get_boot_security`, and `get_uac` are read-only. They disclose the host OS edition, build, uptime, an approximate boot time, whether Fast Startup is configured, safe mode, the count of pending file renames (not the paths), UEFI versus legacy firmware, Secure Boot, test-signing (BCD and the running kernel), WHQL developer test mode, and the UAC policy (EnableLUA and the consent-prompt slider). `list_logon_sessions` and `get_logon_session` disclose who is logged on, which session is the console, and which session interactive tools would use. Client names and addresses are returned only when `includeClientAddresses` is true, and they are not written to the log. The tools do not log off, connect, or shadow a session. The System module is on by default; disable it with `Vestigo:Modules:System:Enabled=false` if that inventory should not leave the machine.

`set_test_signing` writes Boot Configuration Data on the default boot entry. `set_whql_developer_test_mode` writes the kernel code-integrity policy. Both stay off until `Vestigo:System:AllowBootConfigurationChanges` is `true`. Treat a token that can call them as administrator-equivalent: they change driver-signature enforcement and take effect after a reboot. Enabling the option without an entry in `ApiTokens` only logs a `SECURITY WARNING` that names "Boot configuration changes". Vestigo never reboots the machine. Turning test signing on is refused unless Secure Boot is known to be disabled.

`set_uac` writes the UAC policy under `HKLM\SOFTWARE\Microsoft\Windows\CurrentVersion\Policies\System`. It stays off until `Vestigo:System:AllowUacChanges` is `true`. Treat a token that can call it as administrator-equivalent: it lowers or removes elevation prompts, and turning UAC off also breaks UWP and Store apps until it is turned back on. Enabling the option without an entry in `ApiTokens` only logs a `SECURITY WARNING` that names "UAC changes". Vestigo never reboots the machine. `EnableLUA` changes take effect after a reboot.

## Power

`get_power_state` and `get_sleep_configuration` are read-only. They disclose AC status, battery percent and charging, the active scheme name, approximate last sleep and wake times, and the AC/DC lid, timeout, wake-timer, and hybrid-sleep settings. They do not name processes and they do not change the scheme. The module is on by default; disable it with `Vestigo:Modules:Power:Enabled=false`.

## Remote debugger

A running `msvsmon.exe` lets any authenticated remote debugger attach to processes and execute code as the user the monitor runs as. `start_remote_debugger` therefore defaults to Windows authentication; use `allowUsers` to limit who may connect. `auth: none` runs `/noauth /anyuser`, which disables authentication completely: anyone who can reach the port gets code execution. It needs `iUnderstandNoAuthIsInsecure: true` and writes a warning to the result and the log. Use it only on isolated networks and stop the monitor afterwards. Vestigo binds only `ListenAddress`, but `msvsmon.exe` listens on the chosen port on all interfaces, subject to the firewall (`prepare_remote_debugger_computer` changes firewall rules).

`install_remote_debugger` downloads over HTTPS and runs the installer as the service account (normally SYSTEM) only when `WinVerifyTrust` accepts its Authenticode signature and the signer CN or O is exactly `Microsoft Corporation`. The signature is checked with `WTD_REVOCATION_CHECK_CHAIN`; an offline machine or a host that cannot reach a revocation endpoint may reject the installer. `stop_remote_debugger` only accepts processes that are running `msvsmon.exe`. The module is off by default because it installs software and launches `msvsmon.exe`. Enabling it with `Vestigo:Modules:RemoteDebugger:Enabled = true` also requires the `Jobs` and `Processes` modules, so without `ApiTokens` the server logs a `SECURITY WARNING` and anyone who can reach it can run programs.

## Devices

The Devices module installs and removes drivers, creates device nodes, edits class filters, and restarts, enables or disables devices. Drivers run in the kernel, so a client of these tools can run code with kernel privilege on the host; this is by design for driver development. Mutating operations need an elevated service account; read-only queries mostly do not. Controls: the module is disabled by default and must be enabled explicitly (`Vestigo:Modules:Devices:Enabled`), set `ApiTokens` whenever it is enabled on a shared machine (loopback does not isolate local users), INF paths must be existing `.inf` files inside a `Read` root, nefcon arguments are fixed (never free-form), GUIDs and instance IDs are validated, and only one nefcon process runs at a time with a timeout. Vestigo never triggers a reboot. Treat any root that contains drivers as trusted input.

## Diagnostics

The Diagnostics module reads PE metadata and Authenticode results for files inside a root with `Read` access, lists modules loaded in a running process, and can disclose SetupAPI history, device problem evidence, graphics adapters, process connections, media capabilities, and Windows Error Reporting metadata. That is information disclosure, so the module is off by default (`Vestigo:Modules:Diagnostics:Enabled`). Enabling it without `ApiTokens` is allowed and logs a startup `SECURITY WARNING` that names Diagnostics separately from administrator-equivalent modules. The warning also names TCP and UDP bindings, Media Foundation encoders and camera formats, audio format checks, and crash-report metadata. When `Vestigo:Diagnostics:AllowOnlineRevocation` is also set, that warning says signature checks may contact revocation servers. Capture probes, network probes, audible audio playback, and process dumps are named only when their own gates are on.

`verify_file_signature` with `revocation: none` or `cacheOnly` sets `WTD_CACHE_ONLY_URL_RETRIEVAL` and does not use the network. `online` is refused with `revocation_not_allowed` until `AllowOnlineRevocation` is true. `stat_path` always uses `cacheOnly`. A result of `unavailable` means the check could not be completed (for example the catalog service failed) and is never reported as unsigned. A `valid` result is an Authenticode observation. It is not a decision that Windows will load the file as a kernel driver. The remote-debugger installer keeps its own stricter Microsoft signer check.

`list_process_modules` enumerates with Toolhelp. `includePaths` returns a `root:relative` alias only after the path is canonicalized, so a symlink or junction that leaves a Read root is `path: null` and `pathOutsideRoots: true`. Absolute paths are not returned in results, errors, or logs. The CodeView PDB path from `inspect_binary` is reduced to a file name. The module list is a best-effort snapshot, not an atomic identity with a later file inspection.

`get_device_install_history` reads the fixed SetupAPI dev logs under `%windir%\INF`. Callers cannot name a file, and `RootPolicy` does not apply. The log can quote system INF paths and driver-version lines. `includeRaw` is false by default; with it false, section text is not returned and is not written to the Vestigo log. `explain_device_problem` repeats the structured facts (exit status, file name, codes) and does not attach raw section text. Device-node queries use the same read-only device interface as the Devices module and do not restart, enable, or disable devices.

`list_graphics_adapters` discloses adapter names, PCI ids, memory sizes, and driver versions from the service process. `probe_capture_support` runs in the console user's session and reports whether frames arrive. It does not copy pixels into results, logs, or spool files. It stays off until `Vestigo:Diagnostics:AllowCaptureProbes` is true. The MSI exposes that gate as an unchecked child of Diagnostics. The startup warning names capture probes only when that gate is on.

`list_process_connections` discloses local TCP and UDP bindings for one process. Remote addresses and ports are returned only when `includeRemoteAddresses` is true, and they are not written to the log. The tool does not read packet payloads, HTTP headers, or credentials, and it does not return endpoints owned by other processes. `test_endpoint` stays off until `Vestigo:Diagnostics:AllowNetworkProbes` is true and the requested host, or host and port, is listed in `Vestigo:Diagnostics:AllowedProbeDestinations`. The installer owns the boolean gate and does not rewrite the allow-list. The direct probe connection contacts only that one destination, from Vestigo's own network context, which can differ from an application's routing, proxy, or credentials. TLS checks keep certificate name and chain validation. Chain building may also contact Authority Information Access issuer servers. Online revocation runs only when `Vestigo:Diagnostics:AllowOnlineRevocation` is true, and then it may contact revocation servers. The startup warning names network probes only when the gate is on.

`list_video_encoders` discloses Media Foundation encoder names and media types. It does not activate those transforms. `list_camera_formats` discloses camera names, symbolic links, and advertised formats. Selecting a device activates that capture source only long enough to read the types, which can light a camera indicator, and then shuts the source down. It does not read samples. `probe_audio_format` runs in the console user's session. A format check does not start the audio stream. A synthetic tone plays only when `Vestigo:Diagnostics:AllowAudioPlayback` is true, only on a render endpoint, and only in shared mode. The tool does not change the default endpoint and does not record a microphone or loopback. The startup warning names audio playback only when that gate is on.

`list_crash_reports` discloses crash metadata from the fixed machine WER stores and from each user profile: application name and path, event type, and signature values. It does not return dump bytes or the raw report file. `capture_process_dump` stays off until `Vestigo:Diagnostics:AllowProcessDumps` is true. It writes a minidump as the service account into a root with Write access. A `full` dump contains process memory, which can include credentials that were in the process. The tool refuses the Vestigo service, pid 4, a fixed list of critical processes, and protected processes. It checks the process start time again immediately before writing. The file is deleted when the write fails, is cancelled, or exceeds `Vestigo:Diagnostics:MaxDumpBytes`. If that delete fails, the original dump error is kept and the job also reports `cleanup_failed`. Vestigo does not upload the dump and does not create a download ticket. The startup warning names process dumps only when that gate is on.

## Debug output

`start_debug_capture` reads every `OutputDebugString` message that reaches the session `DBWIN_BUFFER` (and, outside session 0, the Global buffer). That includes messages from other users' processes. The capture runs as the service account. Treat a token that can call these tools as able to observe debug output from the whole machine. The module is off by default (`Vestigo:Modules:DebugOutput:Enabled`). Enabling it without `ApiTokens` is allowed and logs a startup `SECURITY WARNING` that names DebugOutput separately from administrator-equivalent modules.

DebugViewConsole is bundled, not downloaded at run time. The build pins the DebugView++ 1.30.0.0 `DebugViewConsole.exe` asset by URL and SHA-256 (`build/DebugViewPin.cs`). The file is not Authenticode-signed by Nefarius, so Vestigo re-checks the hash before every launch (unless `Vestigo:DebugOutput:ExpectedSha256` is empty for an administrator-overridden path). Arguments are a fixed list with no shell; filter values that are empty, start with `-`, or contain control characters are rejected. Only one capture runs at a time. On startup Vestigo kills only a recorded orphan whose image path still matches the owned `DebugViewConsole.exe`.


## Windows servicing

`WindowsServicing` is disabled by default, requires Jobs, and warns at startup
when enabled without API tokens. It exposes update history, package identities,
service/process names, Windows-volume space and fixed servicing-file metadata.
Raw pending-file queue paths can contain user/software names and are returned
even outside configured roots; queue inspection never opens those files.

CBS/DISM log content and caller-selected file-locker queries require existing
Read roots. No additional roots are granted automatically. Logs can contain
sensitive machine/user data. Event evidence uses bounded existing event-log
queries. Native DLL imports are restricted to System32 and COM objects are
released on the MTA that acquired them.

Offline WUA applicability queries can perform local work and update WUA caches
or logs; DISM enumeration can write its own logs. No installation, repair,
online scan, restart, queue edit or process shutdown is requested. Jobs use the
existing retention/output caps. Timeout/cancellation does not terminate native
Windows work; its concurrency slot remains held until completion. A stuck call
requires operator investigation. Restart Manager results are best-effort and
are not permission to replace a file. See [Windows servicing diagnostics](windows-servicing.md).
